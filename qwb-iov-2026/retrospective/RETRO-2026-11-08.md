## 2. 引擎层复盘（这一节是本场最值钱的部分）

### 2.1 P0-A：**planner 从头到尾就是坏的**（本场最硬的发现）

**新证据（比"模型太弱"严重得多）**

1. 整个会话里 `reason_done` 事件共 **641 次，其中 `raw_response_finish_reason="error"` 641 次、
   非 error 0 次**；`raw_response_chars=0`、`raw_response_sha256=e3b0c442…`（空串的 sha256）⇒
   planner 的模型调用**每次都返回 0 字符**。
2. `state/sessions/*/workspace/.muteki-agent-state/reason/draft.json`：**29/29 个 run 都是
   `{"committed": false, "operations": []}`** ⇒ 从来没有一次成功提交过 draft。
3. `.../reason/plugins.json`：**29 个 run 的 `tools` 全是 `[]`**（planner 的 MCP 插件工具目录为空）。
4. **时间线**：最早一次 `reason_done` 是 **11-07 19:26**（赛前搭建当晚），一直失败到 11-08 11:52。
   ⇒ 不是比赛中途坏掉的，**这套环境从装好起 planner 就没工作过**，与我的 09:20 并发调整无关。
5. 我用最小命令复现了同样的症状：`pi -p --mode json --no-session --no-builtin-tools --provider deepseek …`
   在 agent 目录里没有 provider 凭据时会打印 `No API key found for deepseek.`，**stdout 无 assistant 文本、
   退出码 0** —— 与事件里"0 字符 + status received"的形态完全一致。
   `~/.ctfagent/.s1-agent/auth.json` 实测是 `{}`（空），即 pi 的 provider 凭据不在那里。

**为什么这决定了整场成绩**

- planner 只在"worker 一轮结束、需要再规划一步"时被调用。它 100% 失败 ⇒ **任何需要第二步的 run 必死**
  （192 代 `runtime_failure`）。
- 三道解出的题都是"第一代就拿到 flag 或少数几代内收束"的形态，绕过了 planner。
- 面板的 223 次 `run.resolve` 又不断重启 worker（每代 4–5 分钟），让"看起来在推进"，掩盖了 planner 已死。

**根因（A 已被现场复现坐实）**

| 候选 | 依据 | 验证方式 |
|---|---|---|
| **A. planner 的 pi 拿不到 provider 凭据（`reason/pi-agent/` 从未被 stage）** ✅ **已确认** | 最小复现输出 `No API key found`；且 32 代的 run 里该目录始终不存在 | 已做（见下） |
| B. `--provider` 名与 staged `models.json` 里的 provider id 不一致（账号是 `custom_endpoint`，`--provider deepseek` 查不到） | 账号配置里 `provider_id: ""`、`base_url=deepseek.com` | 看 planner 的 `models.json` 里 providers 的 key |
| C. 决定工具（`open_step/commit/...`）没被 `--tools` 真正暴露 | `plugins.json tools=[]`（但那只是 MCP 插件工具，extension 工具另算） | 在 planner 进程里 `pi -p --tools read,commit --extension …` 看工具列表 |

**现场复现（本轮追加，坐实机制）**

用真 run 的 graph.json + 引擎同款参数，**不提供 staged `pi-agent` 目录**跑一次：

```bash
pi -p --mode json --no-session --no-context-files --no-builtin-tools \
   --extension muteki/solver/pi_decide_extension.ts \
   --tools read,open_step,peek_step,preview,commit \
   --system-prompt "..." 'facts: none'
# → No API key found for the selected model.
#   stdout 只有 session 头、无 assistant 文本、退出码 0  ← 与事件里的「0 字符 + received」完全一致
```

而 `.muteki-agent-state/reason/` 里 **只有 graph.json / draft.json / plugins.json，没有 `pi-agent/` 目录**——
但引擎的 planner 调用明确要求 `agent_state_dir=<reason>/pi-agent`（`usage_routes.py:71` 也按这个路径找 models.json）。
即：**worker 的凭据目录会被 stage，planner 的没有** ⇒ planner 每次都在鉴权处就死了。

**修复建议（下次开赛前必做）**

1. **用一个真跑得通的 planner 冒烟用例**写进 `preflight`：给定 3 条事实，要求 planner 输出一份
   `committed=true` 的 draft；不通过就 `NO-GO`，不允许开赛。今天的 `preflight` **完全没有覆盖这条**。
2. planner 的 pi 调用要**记录 stderr 与 argv**（现在只有 0 字符的结果，没有任何诊断信息）。
3. 修好之前，**把 planner 失败降级为优雅收束**：worker 一轮结束就结束，不再 `runtime_failure` 判死，
   也不再触发 223 次 reopen 的空转。

### 2.2 P0-B：重启循环把成本放大了一个量级

**证据**

- `run.resolve` 命令 **223 次**（`platform.db.command_ledger_index`），来自 `/api/runs/{id}/resolve`（外部调用，可能是面板按钮）。
- `apps/web/run_lifecycle.py` 的 reopen 路径里 `persist_run_launch_limits(..., renew_execution_budget=True)`
  —— **每次 reopen 重置续做预算**；worker profile 的 `max_continuations: 3` 因此形同虚设（实测单 run 32 代）。
- 单个 run 生命周期：`finished(no_progress)` → `reopened(resolve)` → `preparing` → 新 worker → 4–5 分钟又 `runtime_failure` → 再 reopen……

**影响**：`run-51063`（last_ignition）32 代、28.3M token；`run-144625`（重卡）28 代、37.1M token。
如果只保留前 3 代，成本能砍掉 80%，且解出题的三条线（5–17 代）说明"多代"确实有用——
**问题不在多代，在于每代都在重复注入 94% 的重复事实 + 每代都要重新规划**。

**建议**
- reopen 时**不重置**执行预算，改为按 run 计总预算（如 6 代 / 25M token 硬顶）。
- 面板上的"继续解题"按钮要显式二次确认 + 显示该 run 已用代数/成本。

### 2.3 P0-C：黑板事实 94% 是重复文本，直接把上下文撑爆

**证据**（同文本去重后统计）

| run | 事实事件 | 其中重复 | 重复率 |
|---|---|---|---|
| run-51063 | 528 | 496 | **94%** |
| run-40288 | 474 | 445 | **94%** |
| run-144625 | 471 | 442 | **94%** |
| run-35254 | 449 | 423 | **94%** |

同一段事实会以 `fact_added` + `observation_added` + `intent_concluded` 三种事件各存一份，
且每次重启由 bootstrap 重新发布一遍。**这就是 34k token/工具调用的直接原因。**

**建议**
- 黑板发布前按内容哈希去重（我在 `tools/keep_light.py` 里已经实现了事件层去重，可下沉到引擎）。
- prompt 里只注入"最近 N 条 + 摘要"，全量事实留在板上按需检索。
- 目标：**token/工具调用 从 34k 降到 5k 以内**（预计同预算下能多跑 5–6 倍的工作量）。

### 2.4 P1-A：`wall_clock_budget` 对手工 run 不生效

实测单 run 墙钟 18–171 分钟，远超 `wall_clock_budget=900`。`tsec_eval` 的 visit 时间盒为 0，
手工派发的 run 没有外部计时器 ⇒ 只能靠人看。我临时写了 `tools/watchdog.py`（22 分钟 + 空闲 5 分钟自动 stop）补位。

**建议**：把手表放进引擎（`run.start` 时注册墙钟定时器），而不是依赖外部脚本。

### 2.5 P1-B：事件流膨胀拖垮面板（已修，但要固化）

- 一个 run 的事件流 40–50MB / 19–22 万条，其中 **99% 是 `reasoning.delta`**（一个 token 一条）。
- 面板打开任意 run 会从 `seq=1` **全量重放**，经 Next 代理 3 秒只吐出 38KB ⇒ 打开要 20 分钟。
- 赛中处理：`tools/keep_light.py` 定时压缩（删 reasoning + 黑板去重），438MB → 34MB，
  重放吞吐 38KB/3s → **1.5MB/3s（45×）**，打开变秒级。

**建议**：engine 侧直接把 reasoning 写独立文件、或按 1.2s/160 字合并（`ctfagent watch` 已经是这么做的），
面板默认走 `?replay=batch&after=<last>` 而不是全量重放。

## 4. 逐题复盘

### 4.1 ✅ iov-重生的种子（run-37596，86 min / 15.0M / 428 工具）

- **题面**：BCM-A3 产线诊断密钥灌注，7·14 工位连续电压跌落 → 灌注记录异常；私钥写入后从未导出。
- **路径**（agent 自己走出来的）：OTA 解析（`BCMOTA01`，BE 表项 64B）→ rootfs cpio → `BCM-DIAG1` bundle →
  **ML-KEM-768** 参数 → `fault_slots=3,9,14` 三槽种子复用 → 恢复共享 `s` → 跨槽差分 K_fin → 
  `AES-256-GCM(key=SHA256(kdf_prefix‖K_fin9), nonce=payload[0:12], aad=payload_aad)` → flag。
- **关键转折**：13 代之后才收敛；中间的"新阴性"记录（1.01M 组 AEAD + 151×14 种流密码 0 命中）说明它在**有边界地排除**。
- **可复用产物**：`shared/ks_search.py`（已知明文 `flag{` 驱动的 keystream 扫描）、`shared/se.pkl`。

### 4.2 ✅ re-Route97 的副歌（run-63775，82 min / 12.9M / 345 工具）

- **路径**：`dashboard.png` 尾部 `AJ9U2026` + 16B（LSB 层非简单打包）→ `radio_channel.wav` 的 chunk 解析
  （size 向上取偶才能到 flgx@0x69c0）→ 三段谱面表解密（`ach1^0xA7`…）→ `route97_rhythm.exe` 的 unicorn 模拟 →
  以现场 state init 为初值的 Python mix 模型逐 note 求解。
- **亮点**：wine 用了 **43 次**（本场最高），unicorn 5 次、angr 2 次 —— 这是 dsh 时代几乎没有的工具行为。
- **卡点历史**：先按 fact_009 推的初值错了，靠 trace 在 `0x402702/0x402733` 断点 dump 寄存器把初值纠正过来（自我纠错闭环）。

### 4.3 ✅ NL-BCM 车身控制器（run-363803，18 min / 2.9M / 120 工具）

- **路径**：DoIP(ISO 13400) `<target>:32783` → 路由激活 SA=0x0E00 → payload type 0x8001 →
  **UDS 0x23 ALFID=0x44** 读 `0x08000000..0x08000FEF` → 用 FWPK 头 `0x13572468` 走闪存解密函数还原 0x1258 字节引导镜像 →
  payload 偏移 `0x1270` 拿到《NL-BCM 车间刷新说明》→ flag。
- **效率最高的一题**（2.9M token，是平均的 1/6）：**离线 + 判据自证 + 一次性交互协议**。

### 4.4 ❌ iov-车内总线摆渡（run-914360 / 1314315 / 1611990，合计 23M token）

- **已拿到的硬货**：
  - SOME/IP：`service=0xbeef`，16B 大端头 + JSON；`isotp` 键 = `[ISO-TP PCI][UDS]`；`0x7e0` 请求 / `0x7e8` 响应；
    `0x0101 {"can_id":"0x7e0","isotp":"022701"}` 能拿到 `67 01 + seed`（seed 每次随机）。
  - 方法号全空间 65536 枚举：只有 `0x0001/0x0101/0x0201` 可达。
  - **`gateway-calibrator` 隐藏分支 `argc==31337` 打印两个明文密钥**：
    `can-uds-security-key-qwb-2026!!!` / `flexray-static-auth-key-qwb-2026`（这是 run-1611990 挖出来的）。
- **为什么没解出**：靶场 **10:45 起持续 `Connection refused`**（三个 run 独立采样到 11:03，UDP 30490 也超时，
  无 restart 入口），拿到密钥也没法用。**这不是模型的锅。**
- **教训**：`0x27` SecurityAccess 的 key 派生试了 638 种候选全 `7f2735`——现在看，密钥就在 calibration 工具里，
  **应该优先把附件里的二进制"所有分支/所有 argv 组合"穷举**，而不是先去猜 UDS 密钥算法。

### 4.5 ❌ re-LastIgnition（run-51063 / 1314496 / 1995778，合计 45M token，本场最贵）

- **已拿到的硬货**：
  - 校验链完整逆出：`H1=SHA256(b"LI7/view\0"+cred)` → `0x140004D70`（779 字节字节码 VM 壳）→
    `HMAC-SHA256(key=H1, msg=b"LI7/tag\0"+bundle[0:0x24]+bundle[0x44:]) == bundle[0x24:0x44]`。
  - **离线 oracle 0.115 ms/候选（8 核 ≈69k/s）**，不必跑 wine。
  - 每帧 48B 里只有 `[24:32]`+`[34:42]` 两块 8 字节有信息量（被 `00 00` 隔开，字节流不连续）。
  - `bcrypt AES` 链用的是 **`.data 0x1400ef2e0` 的静态密钥**（`cce8947f…`），不是运行时派生。
  - 结论：cred 只被用于 KDF，没有"期望值比较"；唯一门禁是整包 HMAC ⇒ cred 必须是 H1 的 SHA256 前像。
- **为什么没解出**：结构性。除非 cred 本身低熵（比如就在 CAN 三份日志的 A/B 块里），否则不可逆。
  已穷举 **128 万窗口当 H1 + 260 万当 cred**，0 命中。
- **教训**：45M token 里至少一半花在"重启后重新确认已知事实"。**跨代记忆没有摘要机制**，这是引擎问题。

### 4.6 ❌ iov-静默译码（run-40288，171 min / 17M / 555 工具）

- **已拿到的硬货**：OTA 容器 100% 解开；HQC 参数（n=1153/n1=3/n2=384/omega=16/ber=0.10）；
  `pk=(h,s)`、`session=(r1,r2,e)` 三条 weight=16 的稀疏向量全泄露；LLR 是软信息；payload 是 AEAD 密文；
  平台侧姊妹题 README 提示 **flag 载体可能是 64 位十六进制**。
- **负数**：短消息爆破 **17 亿次 GCM 认证验证**（k1=1/2 穷尽 × 6 序列化 × 11 KDF × 16 种容器切分 × 3 AAD）0 命中；
  且发现 **payload 只有 75B，装不下 `n12|ct48|t16`(=76B)**，说明切分假设本身不自洽。
- **下一步唯一有价值的方向**：反汇编 `fw-diag` 读真实 k1/KDF 布局；或换 RM(1,7) 的 Walsh-Hadamard 软判据。

### 4.7 ❌ iov-猎隼折翼（run-35254，169 min / 14.6M / 459 工具）

- **已拿到的硬货**：`pk` 是 FALCON-512 形态但**是诱饵**（14bit 解包 max=16285>q=12289，NTRU 不成立）；
  `profiles` = 63 类模板；侧信道对齐被彻底解开：`replicate=2` 是"32 样本观测 + 紧邻 32 样本副本"，
  `trace_indices` 是**窗口序号**不是样本序号，配对后 256 对 100% 合法（invalid=0，巧合概率 1e-34）；
  491/512 无歧义，值域 -15..11、σ≈4（正是 FALCON 秘密系数分布）。
- **卡点**：只剩"密钥序列化 + KDF 形式"，已扫 7×18×40×5×4 全 0 命中。**这是纯猜形式**，不是分析能力问题。

### 4.8 ❌ misc-CAN言乱语 / 重卡（run-144625，165 min / 37.1M / 850 工具，本场最贵）

- **已拿到的硬货**：`blackbox.blf` 613 个 zlib LOBJ → 1,671,948 条 CAN 帧；`shards.zip` 256 张灰度图可精确拼回
  16×16 文档（标题 `WO-0113/GATEWAY SHIFT AUDIT`，重叠 2px、步长 32，像素级相等判据）；
  `chain.txt` 的 base32/64/hex 分支经 BFS 确认唯一；`drive.gif` 存在**可复原静止底图**（+3px/帧补偿后
  std=0.0645 vs 噪声 0.043，推翻了前一代"均匀噪点"的结论）。
- **为什么贵**：四路材料（BLF/GIF/WAV/ZIP）在一个 run 里并行推进，每次重启都要重新对齐。
  **这题应该拆成 4 个独立 run**，每路一个判据。

### 4.9 ❌ misc-日志的秘密（run-107924，166 min / 17.5M / 513 工具）

- 大量**有界负结论**：口令不是 name/image_sha256/ts 的 1–3 段拼接在 blake2b/shake/ripemd 族下的派生；
  228B 快照对"周期≤64 的加法/乘法重复密钥流"不可行；口令 token 与 image_sha256 的 8 字节窗口无常数掩码关系。
- 这类"排除法"工作本身是对的，但**没有收敛判据**：每代都在扩排除表，没人问"如果都不是，那它可能是什么结构"。

### 4.10 ❌ misc-么什有里包量流（run-98091，167 min / 18M / 491 工具）

- 52001 gzip 独立复核（首错 distance=1672 赤字 82，不可能是标准 deflate）；83,754 个参数派生密钥
  × 三资产 × CTR/CFB/OFB/CBC 已知明文块判定 0 命中。
- 同样是"排除法长跑"，缺少"换模型/换判据"的强制点。

### 4.11 ❌ iov-Autopilot（run-2703728，75 min / 10.9M / 368 工具）

- 已确认：`fusion_node` 里 `FUSION_KEY` 只被死代码打印函数引用（无实际用途）；`.bss` 对象区恰好 0x30000；
  13 个猜测的 SM4 工程密钥都解不出可读 OTA 明文；rootfs 里没有 `/proc`、没有 shell/python。
- 平台公告提示"只改一层不够，记录仪会核对各层记录是否同属一次事件" ⇒ 需要构造**跨层自洽的幽灵事件**，
  但 agent 一直停在"找密钥/找入口"的层面，没有转向"伪造多层记录"。

## 5. 模型评估：dsv41f（deepseek-flash）到底行不行

### 5.1 它做得好的（有证据）

| 能力 | 证据 |
|---|---|
| 逆向执行 | `last_ignition` 的 779 字节字节码 VM 被完整反汇编；SOME/IP 的 `isotp` 字段名靠 fuzz 试出来 |
| 协议复原 | DoIP 路由激活 + UDS 0x23 ALFID=0x44 一次打通；SOME/IP 头部判别器（service/proto/iface 组合）被精确钉死 |
| 工具驱动 | wine 109 次、gdb 88、r2 142、angr/unicorn 51 —— 不是"只会写 python" |
| 自我纠错 | re-Route97 里自己发现初值推错，用 trace 断点改正后重新建模 |
| 有界排除 | 大量"新阴性"条目，且写明边界（数量、维度、命中判据） |

### 5.2 它做得不好的

| 病灶 | 证据 | 归属 |
|---|---|---|
| 不会"收束" | 192 代死在 planner draft；worker 每代末尾都不给"结论/下一步" | **引擎 + prompt 双因** |
| 重复劳动 | 94% 事实重复；跨越 5–32 代反复确认同一结论 | **引擎记忆机制**（没摘要、没去重） |
| 不会换假设 | 静默译码/猎隼/流量包：排除表越写越长，但不主动换模型/换判据 | **模型**（缺"元认知"） |
| 优先级判断差 | 重卡四路并行、last_ignition 反复滑窗，都是"平均用力" | **模型 + 调度** |
| 对公告/提示的利用弱 | 白名单公告灌进去后跑了 129 种派生才收；Autopilot 公告没转成"伪造多层记录" | **模型 + prompt** |

### 5.3 判断

**"dsv41f 到智商上限"这个说法要拆开看**：
- **在"单步执行 + 工具调用 + 有界排除"上，它没有明显天花板**——本场的 3 道题和大量硬结论都是它做出来的；
- **在"多步元认知（换假设、拆题、判断该不该继续）"上，它确实不够**——这是 10 道未解题的共同病灶；
- **但本场最大的损失不是模型**：planner 判死（192 代）和靶场中途挂掉，任何一个不发生，成绩都会明显不同。

**换 GLM 的正确验证方式**（不要只看总分）：
1. 用**同一批题**（`run-51063` 的 last_ignition、`run-40288` 静默译码、`run-35254` 猎隼）跑 AB，因为它们的
   "结构与卡点"已经被我们摸清，**判据可自证**，不需要人盯着；
2. 对比四个指标：**代级解出率、token/工具调用、事实重复率、交不出 draft 的比例**；
3. 特别看"换假设"能力：给同一个死局（如 `h·r ≠ h/s`），看它几次尝试后主动换模型。

## 7. 与"极氪 2026"的对比：需要什么数据

你的直觉是"极氪那次更好"，但两场不可直接比。要判断是**架构/模型**的问题还是**题目分布**的问题，需要：

1. 极氪那场的：题数、解出数、每题耗时、**是否有容器/动态环境题**、团队分工（几人同时做题）；
2. 那场的 run/会话是否留了 token 记录（若无，只能用"题/小时"和"题/人"这种粗指标）；
3. 那场的题型分布（web/pwn/crypto 多，还是固件/逆向多）。

我的先验判断（可变）：**极氪可能 web/交互类偏多，而 DS 在这类题上"写脚本打接口"很强**；
本场是固件/离线逆向为主，恰好是"长链路 + 需要换假设"的题，踩中模型弱点。
换句话说：**换 GLM 值得做，但别指望它单独解决问题——planner/记忆/预算是本场更大的杠杆。**

## 8. 时序复盘：钱花在哪、什么时候该停

| 时段 | 活跃 run | 工具调用 | 事实事件 | 解出 |
|---|---|---|---|---|
| 09:00–09:30 | 9 | 1344 | 65 | 0 |

| 10:30–11:00 | 12 | 1121 | 96 | 0 |
| 11:00–11:30 | 11 | 961 | 1430 | 0 |
| 11:30–12:00 | 7 | 546 | 1496 | 0 |

**三个解出全部发生在 10:30 之前。之后 90 分钟 0 解出，却花掉一半的钱**：

| 区间 | token | 折合 | 解出 |
|---|---|---|---|
| 09:00–10:30 | ≈111M | ≈$33 | 3 |
| 10:30–12:00 | ≈103M | ≈$31 | **0** |

10:30 之后花得最多的：`run-144625` 18.8M、`run-51063` 16.6M、`run-2703728` 10.9M、`run-40288` 9.8M、`run-107924` 9.3M

而是重启次数变多、每代把黑板全文重新发布一遍（94% 重复）。

1. 设一个**止损线**：连续 45 分钟无新解出，就停止"派新 run"，转人工/换题/WP 收尾（本场可省 $20+）。
2. 题级预算：单题 ≤ 15M token，超了强制收束并把"下一步"写进笔记。
3. 未解出的题在最后 30 分钟只做**证据固化**（截图/命令/结论），不再尝试新假设。
