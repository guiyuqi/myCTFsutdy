## 0. 一句话

这题是**三层套娃**：字节反转的 pcapng → 弱私钥 ECDH + HKDF 的 AES-GCM 密文 → 里面又是一份
pcapng（DoIP/UDS 资产清单）→ 清单指向 3 个加密资产 + 2 条中文提示。
**前两层我们全解开了（可复现）**；第三层卡在两个地方：
① 81 组参数密钥的 KDF 形式没猜中；② 0e81 那条 gzip 流在帧边界上有字节级缺失/插入，
需要全局 oracle（gzip footer）才能定分支，而当时一直在用"输出全是 base64"这种弱判据。

## 2. 已解开的链路（可复现）

### 2.1 外层：反转 + magic 修正

```bash
python3 - <<'PY'
d = open('gnpacp.619','rb').read()
rev = d[::-1]
hdr = rev.index(b'\x1a\x2b\x3c\x4c')          # SHB 的 byte-order magic
rev = rev[:hdr] + b'\x1a\x2b\x3c\x4d' + rev[hdr+4:]   # 改成标准 4d
open('fixed.pcap','wb').write(rev)
PY
tshark -r fixed.pcap -q -z io,phs      # 1×SHB + 1×IDB + 379×EPB，时间 2026-10-28 13:17:24
```

- 反转后恰好把原大端 pcapng 字段变成小端；唯一异常是 SHB magic 末字节 `4c`（标准 `4d`）。
- 379 包里只有 2 类载荷：1 条 UDP 39001 握手 + 378 条 TCP 39002→443 数据。【已核】

### 2.2 握手（明文 ASCII）

```
DGPT/1 HANDSHAKE
gateway=GW-2241
peer_pubkey=0439daf267869de081f789324098661a15bb89d0874dde29ddba88c0c08a6329d29933f25abc0170dff9e7544c57f59ff0599b8653163ea8dcac923a1c5b00759d
ephemeral=040b484a0c2055301c67703c4bc0a1af3013dcfa7171345d59d7dba5d3ccfb7c0c0c6a233e2e4155c18348eb31faebdf661cf47a060df88251448832032ae311a6

```

`key_epoch=legacy-8bit` 就是"弱私钥"的明示：**静态公钥的私钥只有 8 位**。【已核】

### 2.3 弱私钥：BSGS 求小离散对数

用纯 Python secp256r1 算术 + BSGS（range 2^32）对两个公钥求小标量：

- `peer_pubkey` → **k = 137**（唯一命中，`137*G` 与公钥逐字节相同）；
- `ephemeral` → 2^32 内无解（临时私钥不是小标量）。

共享点 `S = 137 * ephemeral`，取 `z = x`：

```
x = 1368b59cd69e797d13f44037b981404b859daf9a73e2da7c892ece8ea4ef4cfa
y = 3e1c4a8276b52a67e6843ebcb2bae2d7ada644a86aee9428b01033f40e23ae0e
```

> 踩过的坑：`shared/shared_x.txt` 里存了 **两行**（x 和 y）。复现时只取第 1 行；
> 一次性把两行拼成 64 字节会得到错误的 HKDF 输入（我第一次复现就踩了，`InvalidTag`）。

### 2.4 派生与解密（一次命中）

```bash
python3 - <<'PY'
import hmac, hashlib
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
x = bytes.fromhex(open('shared/shared_x.txt').read().split()[0])
nonce = bytes.fromhex('4d5ff53f0e92f66463b7d801')
def hkdf(ikm, salt, info, n=32):
    prk = hmac.new(salt, ikm, hashlib.sha256).digest(); okm=b''; t=b''; i=1
    while len(okm) < n:
        t = hmac.new(prk, t+info+bytes([i]), hashlib.sha256).digest(); okm += t; i += 1
    return okm[:n]
key = hkdf(x, nonce, b'DGPT/1')
print(key.hex())
raw = open('shared/extract/payload.bin','rb').read()
assert raw[:12] == b'DGPT/1 DATA\n'
open('inner.pcapng','wb').write(AESGCM(key).decrypt(nonce, raw[12:], None))
PY
# key = 959d9c3c771c87034cd2f8dc2712060179414444444ba1624ce55db1ccb3ee6c
# 明文 5,281,140 B，magic 0a0d0d0a（pcapng），与 shared/campB/plain.bin 逐字节相同
```

要点：**无 AAD、tag = 记录最后 16 字节、12 字节 IV 直接用握手 nonce**；
`zlib.crc32(密文) == 0xd6de6047` 与握手声明一致（这个 crc 校验的是**密文**，不是明文）。【已核】

> 教训：中间有一轮（fact_003）用"可打印率"判据说"HKDF(x,nonce,'DGPT/1') 已排除"——
> **错**。同一个参数在一轮后用 GCM tag 全量校验一次命中。判据越弱，越容易把真路径排除掉。

### 2.5 内层 pcapng：DoIP/UDS 资产清单

4,122 个包，VIN `LSVAM4180E2100001`，UDS 会话：

- `10 03` 扩展会话 → `27 01` 取 seed `11 22 33 44 55 66 77 88` →
  `27 02` 送 key `4b 78 69 1e 0f 3c 2d d2`（**逐字节 XOR 0x5A**，通过）；
- `22 F1A0` 读到清单（267 B，明文）：

```
# workshop asset manifest
# transport: SOME/IP over UDP
# assets are AES-256-GCM encrypted; do you notice the extra bytes before this frame?
name,size,crc32,chunks
wo_2241.png,983917,39d7ed46,707
sample_04.wav,2116878,2a36dc64,1521
blob_07.enc,8395,0b733384,7
```

- `22 F1B3`（0e83 通道，284 B 中文）：「备份说明 …… 本文件不是压缩包，别用 7z/zip 去开。
  **密钥由 4 个参数组合而成，每个参数有 3 个候选：型号 A1/A2/A3；年款 2021/2022/2023；
  工位 W1/W2/W3；批次 B1/B2/B3。用对了才能看到库页头。**」

⇒ 第三层的密钥空间 = 3^4 = **81 组**；"库页头"最自然的读法是 **SQLite 文件头**
（`SQLite format 3\0`）——这一点很关键：当时前几轮的魔数表里**没有 SQLite**，会漏检。【已核】

### 2.6 三个 SOME/IP 资产的重组（长度精确对上）

- 通道：<target>:30501 → <target>:40000/40001 与 → <target>:40002，
  包数 707/1521/7 与 manifest 的 chunks 完全一致；SOME/IP 头 `1234 | method | len=0x057c |
  client=0e80 | 资产 id | 0101a000`，4 B 大端字节偏移，data 1,392 B/帧。
- 按偏移拼接：983,945 / 2,116,906 / 8,423 B；每份前 28 B 是记录头
  （12 B 结构化 `0002/0003/0004` + `00000001` + 零，16 B 随机），
  去掉 28 B 后长度**精确等于** manifest 的 size 列。【已核】

⇒ 28 B 头就是提示里的 "extra bytes before this frame"；manifest 的 `size`/`crc32` 描述的是**明文**
（`crc32(任意密文切片)` 都不等于 manifest 值，已逐一切片核过）。【已核】

## 3. 卡住的两个点

### 3.1 资产解密：81 组参数 × 各种 KDF，全部 0 命中

已跑过的（都是**强判据**：GCM tag 全量校验 / 文件魔数块判定，不是可读率）：

| 扫描 | 规模 | 结果 |
|---|---|---|
| 81 组参数 × 分隔符/标签式/JSON/中文式 × sha256/sha256²/sha512/blake2s/blake2b/md5/sha1/填充 | 22,392 key × 12 framing | 0 |
| 1,296 个格式串 × 1,992 个派生（HKDF 材料三重积） | 2,581,632 key × 9 framing（≈23M 次） | 0 |
| 同上 + 多进程扫器（5.7 µs/次全量 GCM 校验，8 进程 ≈1.3M key/s/framing） | 12.9 万+ | 0 |
| **非 GCM 模式**（CTR/CFB/OFB/CBC）+ AES-128/192 + SHA-384/224 | 83,754 key × 3 资产 × 9 偏移 | 0 |

⇒ "密钥 = 参数串经常规哈希/填充/KDF，IV/tag 取记录头"这一族**已被真正排除**。【已核】

还没跑的：PBKDF2/scrypt **高迭代**（salt=记录头 16 B）、`random.Random(参数串).randbytes()` 这类
**PRNG 派生**、"16 B 随机尾部作 salt + 12 B 头作 nonce"的组合、以及**每块独立 GCM**。

### 3.2 0e81 的 gzip 链：帧边界上有字节级缺失/插入

- 52001 通道 728 帧，`data = TCP payload[15:]`，727×1198 + 763 = **871,709 B**；
  头 `1f8b08005b85e16a02ff`，**尾 `d4f202d7238c1100` = CRC32 `0xd702f2d4` / ISIZE **1,149,987**。【已核】
- 这是**决定性证据**：拼接口径（起点/长度/顺序）在总长度与 member 终点上完全正确，
  所以错误只能是**流内字节级替换/移位**，不是缺帧/乱序/尾部缺字节。
- 首错：`chunk0[10:]` 单独解出 1,581 B（严格 76 字符/行的 base64，违规 0）；
  接着喂 chunk1，在输出 1,590 B 处出现 `distance=1672`（赤字 82）⇒ deflate 引用越界。【已核】

试过并排除的模型（都是"有界负向"，别再重复）：

| 模型 | 结果 |
|---|---|
| 每帧统一丢 s 字节（s=0..40） | 最好 s=5 → 25,090 B 后崩；不是解 |
| 每帧固定切片 (o, L)（71 万组合） | 局部最优 25,286 B；全流无解 |
| 每帧整体轮转 / 单字节删除 | 只有 chunk1 有伪路径，chunk2 即无解 |
| 块序重排 | 用解码器验证：只有 seq 后继能续接 ⇒ **顺序天然正确** |
| 预设字典（zdict=32 KB） | 能消掉首错，但注入 34 个 0x00、28 处行结构违规 ⇒ 假明文 |
| zlib 生成"gzip+预设字典" | Python/zlib 直接报 `Invalid dictionary` ⇒ 该解释在实现上不成立 |

**当时最关键的教训**：用"输出全是 base64 / 行结构"当判据是**不够的**——
deflate 的 copy token 会把前面正确的 base64 字符复制出来，贪心修复得到 1.15 MB "全 base64"，
但 base64→bz2 立刻 `Data integrity error`。真正的 oracle 是 **gzip footer（CRC32/ISIZE）**。【已核】

## 4. 判词：差什么

1. **不是能力问题**：外层（反转 + magic）、弱私钥（BSGS 8-bit）、HKDF+GCM、内层 UDS 解析、
   资产重组（长度精确对上）——每一步都是"可验证的硬结论"，而且多处自我纠错。
2. **差的是两个"形式猜测"**：
   - 资产 KDF：81 组参数 → 还缺**参数如何变成密钥**的那一步（很可能是很土的做法：拼接后直接当 key、
     或 PRNG 播种、或 PBKDF2 高迭代；"用对了才能看到库页头"暗示明文是 SQLite 文件）；
   - 0e81：还缺**每帧边界到底丢/插几个字节**的全局解（以及"为什么"——很可能是生成脚本每帧
     `b64encode` 分块时按 1198 切片，行边界导致每帧吃掉不同字节）。
3. **时间分配问题**：外层+内层只花了 25 分钟；之后 140 分钟几乎全花在 0e81 上，
   而**资产层（81 组）在同一时间只跑了几轮 KDF 扫描**。如果按"提示最明确优先"排序，
   应该先做资产层（提示给了 4 参数、明确说"密钥由 4 个参数组合而成"），0e81 可以放到最后。

## 5. 下次的可执行路线（按性价比）

1. **资产层优先，用 footer/明文 crc 做 oracle**：
   - 先试"参数串直接拼成 32 字节 key（零填充/空格填充）"——注意提示是"组合而成"，不是"哈希而成"；
   - 再试 `random.Random(参数串)` / `hashlib` 播种 PRNG 出 key；
   - 再试 PBKDF2-SHA256 高迭代（1e4/1e5）+ salt=28 B 头；
   - 判定：`crc32(明文)==manifest 的 crc32`（8395 B 的 blob 只要 7.5 µs/次，10^7 量级秒级）或 SQLite 魔数。
2. **0e81 用全局 oracle 做位级搜索**：
   - 终局判据：解出**恰好 1,149,987 B** 且 `zlib.crc32(明文)==0xd702f2d4`；
   - 搜索空间：每个帧边界丢/插 `d_k∈{0..8}`（727 个边界），用**位级 inflate**（`g11_inflate.py`
     已能报告 baddist 与 bit 位置）做 A*/DFS，剪枝用"输出必须落在 76 列行结构"；
   - 备选解释：生成端对每帧做 base64 分块（每帧 1198 字节未必是 3 的倍数 ⇒ 行边界吃字节）。
3. **交叉验证**：三条资产里 `raw_40001` 整文件 crc32 = `0x00067890` 是刻意构造的异常值
   （2.1 MB 随机数据撞上这种结构值概率 ~2^-32），可能是作者埋的线索或校验提示。
