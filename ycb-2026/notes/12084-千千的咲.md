### 3.1 `.utoc` 目录索引 = 明文（不用 Oodle 就能读）

UTOC header 实测字段（`-==--==--==--==-` 魔数后）：

method_name_count=1, method_name_len=32, compression_block_size=65536, ...`

  的 chunk 索引区。

## 七、★ 打通 Oodle（本机零依赖方案，可复用）

UE5 IoStore 用 **Oodle** 逐 64 KiB 块压缩；`oo2core` 是闭源库，本机没有、也不许装。
但 **APK 里的 x86_64 `libUnreal.so` 静态链接了 OodleLZ_Decompress**，于是自己写了个
「进程内 mini 动态加载器」把它跑起来（`scripts/12084-oodle-ucas-dump.py`）：

1. **找函数**：`.so` 里保留了 Oodle 源码路径（`v:\devel\projects\oodle2\core\newlz.cpp`）和
   `OodleLZ_Decompress` 字符串；用 numpy 扫 `.text` 里 `48 8d XX disp32` 形式的 RIP 相对 LEA，
   命中字符串地址 `0x5C5AE02`+ 的指令在 `0x48df8dd` / `0x48dfb5f`，再用 `.eh_frame_hdr`
   （195731 条 FDE 的二分索引）反查出函数起始 **`0x48df8a0`**。
2. **装进进程**：glibc 不认 Android packed relocations（`SHT_ANDROID_RELA` / `DT_ANDROID_RELA`，
   `.so` 里是 `APS2` 流），**LIEF 1.0 能解**：`730,539` 条 `R_X86_64_RELATIVE` + `551` JUMP_SLOT
   + `27` GLOB_DAT。按 PT_LOAD 手工 mmap 到 `0x150000000000`，把 `BASE+addend` 写回每个槽，
   PLT 用 `dlsym(RTLD_DEFAULT)` 绑到宿主 glibc。
3. **坑**：Oodle 报错走 `fprintf/fputs` 且传了 NULL `FILE*` → 会崩；必须在 `logstub.so` 里
   用真编出来的 C 空函数替换（不能用 `create_string_buffer` 的临时页，会被 Python 回收→执行垃圾）。
   `OodleLZ_Decompress` 的 14 参签名 + `fuzzSafe=1`（safe 模式才抗垃圾输入）。
4. **结果**：`libUnreal_patched.so` + `loader2.py` 已可用；对 1408 个块跑下来
   **555 块真被 Oodle 压缩、853 块本来就是裸数据**，得到 **92,147,872 B 的完整解压流**
   （`work/12084_qiqian/oodle/full_uncompressed.bin`）。
   验证：解压后 `background.uasset`、`T_ChisakiSuccessAtlas` 等此前"缺失"的包都出现了。

**重要结论（解压后仍成立）**：
- `WBP_FlagPanel` / `SubmitCell` / `OnTileXXClicked` / `IsComplete` 在 **92 MB 解压流里 0 命中**，
  `UMG`/`TextBlock`/`UserWidget` 也是 0 → **那个 UMG 包只有文件名在 utoc 里，容器里没有它的数据**
  （58 个包同样"只有名字没有数据"，包括 tile_10..15、HairColorMap、多个 ControlRig_*）。
- 解压流里仍**没有** `DASCTF{` / `flag{` / `ycb{` / 任何 UTF-8/UTF-16 中文提示串。

## 十、A 线（utoc chunk 表）判定性结论：**判死**（2026-10-24 收尾）

目标：从 utoc 解出 828 条 chunk 的 (offset, size) → chunk→块区间 → 定位 16 张 tile 的 `.ubulk`。
**结论：这个 utoc 里不存在 chunk 表**（既无 offset 表，也无 size 表）。以下是"测过的、可复现的"否证：

1. **offset 表**：
   - 约简约束「offset 必须 ⊆ 块表 offset 集合（1408 个值）」+ **全文件**（不是只头部）
     扫描 stride ∈ {8,12,16,20,24} × 字段位置 0/4/8/12/16/20 × 起点 `[144, EOF-828*stride]`，
     命中 1767 条但**全部是块表自身的滑动窗口**（起始 19920..20028，match 822..828/828）。
   - 「offset 单调递增且 < ucas 大小」用 numpy 全量扫 stride ∈ {8,12,16} × u64/u32 → 同样只命中块表。
2. **block-index 表**（offset 存成块号，值 ≤1407）：stride 4/8/12/24 全扫 → 只在目录索引区
   （`44294..44770`，119 个 450~720 的**名字索引**）有噪声命中。
3. **size 表**（用「Σceil(size/64K) == 1408 块」这个硬约束）：stride ∈ {4,8,12,16,20,24,32}
   × u32/u64 × 各字段位置 × 全文件 → **0 命中**。
4. **尾部 828×24 区**（`62845..82717`）：`+20` 字段 828 条全是 0/1（标志位），`+12/+16` 为随机哈希
   → 无 offset/size。
5. `DirectoryIndexSize=25901` 的语义确实被我映射错了：`36944..45142`(8198 B) 是目录索引头
   （FString 挂载点 `../../../` + 名字索引数组，名字索引最大到 ~720 → **字符串表比 619 条大**，
   至少 720 条），完整目录索引应为 `36944..82717`(45,773 B)。但即使在把这个区间**整段**纳入
   上述 1~3 的扫描，仍然没有 chunk 表。

**推论**：UE 的 chunk→块区间不是靠 utoc 里的显式表，而是靠"chunk 按 id 顺序连续排布 + 每 chunk
的块数"，本 utoc 不提供每 chunk 的 size，所以**仅凭 utoc 无法定位某个 .ubulk**。
要拿 tile 像素只能：(a) 用块表中"末块短于 64K"的特征反推 chunk 边界（需知道每块真实解压尺寸，
OodleLZ_Decompress 不返回长度，需再找 `OodleLZ_GetDecompressedSize` 类接口）；
或 (b) 直接跑模拟器。

### 12.1 pak 索引结构（实测，全部字段互证）

`CTFGame-Android_ASTC.pak` 4,625,819 B：

- **FPakInfo 在文件尾**，`rfind(b'\xe1\x12\x6f\x5a')` → `4625615`：
  `u32 magic=0x5A6F12E1 | i32 version=11 | i64 indexOffset=4540310 | i64 indexSize=18506 | 20B indexHash`
  → 之后直接是 **5 个 32 B 压缩方法名槽**（槽0 = `"Oodle"`），`40+20+160 = 204`，
  `4625615+204 = 4625819` = EOF 精确吻合。**本 build 的 FPakInfo 没有
  bEncryptedIndex / EncryptionKeyGuid 字段**（有的话 indexOffset 会对不上，已排除）。
- **主索引** `@4540310`（size 18506）：
  ```
  FString mountPoint = "../../../"        (u32 len=10 含 \0)
  i32 numEntries = 1397
  u64 pathHashSeed = 0xd743bf2d
  i32 hasPathHashIndex = 1 → i64 off=4558816, i64 size=30925, 20B sha1
  i32 hasFullDirectoryIndex = 1 → i64 off=4589741, i64 size=35857, 20B sha1
  i32 encodedPakEntriesSize = 18392
  u8  encodedPakEntries[18392]  @4540420  (到 4558812，其后 4 B 对齐)
  ```
- **encoded pak entry（决定性的一步）**，13 字节/条平均，**1397 条精确消费 18392 B、
  0 异常、offset 单调、块大小之和 == size**：
  ```
  u32 header
      bits31..29 = flags（本 pak 恒 7）
      bits28..23 = compressionMethod（0=None, 1=Oodle）
      bit22      = bEncrypted（全 0）
      bits21..6  = compressionBlockCount
      bits5..0   = compressionBlockSize >> 11   （=32 → 65536）
  u32 offset
  u32 uncompressedSize
  if method != 0:
      u32 size(压缩后)
      if blocksize字段 != 0: bc × u32 每块压缩尺寸      ← 注意：**只有尺寸，没有块偏移**
  ```
  （前人把它当成 `u32 method|u64 offset|u64 size|20B sha1|块表` 的 UE4 写法，
  所以第 3 条起就错位了 —— 真正原因是 v11 用位域 header + 32 位字段 + 只存块尺寸。）
- **FullDirectoryIndex `@4589741`**：`i32 numDirectories=71`，每条
  `FString 目录 | i32 文件数 | (FString 文件名 | i32 location)*`，
  **location 不是序号，而是 EncodedPakEntries 内的字节偏移**（值域 0..18380 < 18392 可验）。
  1397 个文件全部解出，解析结束位置 == 4589741+35857，精确自检通过。

### 12.2 `p.bin`

`CTFGame/Content/Data/p.bin` → location=104 → `method=0`（未压缩）、`offset=39352`、`size=1424`
→ `work/12084b/p.bin`，`md5 78e565f24007045ea018d3b015df9d52`。

**内容结构（1424 B）**
```
+0x00  u64 = 0
+0x08  u64 = 1424      (== 文件长)
+0x10  u64 = 1424
+0x18  u32 = 0
+0x1c  1396 B 高熵载荷 (H=7.85，字节频次 1..15 近均匀，无 4/8/16B 重复块)
```
（可能是 `[u64 未知][u64 usize][u64 csize][u32 flags][data]`；usize==csize 说明"只加密未压缩"。）

**已试且否证的解密路径（全部 0 命中，勿重跑）**
| 尝试 | 结果 |
|---|---|
| 载荷=Oodle / zlib(gzip,raw,auto) | 无块头，`usize==csize`；zlib 三窗口全抛异常 |
| 256 种单字节 XOR（起点 24/28/32/48/52） | 无可读文本 |
| repeating-key XOR，31 个候选 key（chisaki/Chisaki/CTFGame/qiqian/saki/千千/puzzle/flag/PuzzleScriptHost…） | 无 |
| RC4，同上 31 个 key | 无 |
| 重复密钥周期性检测（重合率 L=1..256） | 最高 0.013 ≈ 随机基线 0.0039，**无周期** → 不是重复-key XOR |
| 载荷当 20B 哈希 / 校验和（sha1、md5，起点 20..56） | 不匹配 |

**判读**：载荷是无周期的高熵流 → 流密码（RC4/AES-CTR/ChaCha）或 Oodle 之外的自制加密，
密钥在 `libUnreal.so` 的 `/Script/CTFGame` 原生代码里（该模块字符串已被 cook 剥离，
所以只能按行为定位函数，见 §八 路线 2）。`u64=0` 的头 + 双 size 字段很像
「`FArchive` 自己写的 `TArray<uint8>` 容器 / 自定义 SaveGame 包装」。

### 12.5 静态收口结果（30 min 追加，判死）

**决定性负结论：原生模块里根本没有 `p.bin` 这个名字。**
在 `lib/arm64-v8a/libUnreal.so`（96.5 MB）里，对以下字符串各查 **ASCII / UTF-16LE / UTF-32LE** 三种编码：

| 字符串 | ascii | utf16le | utf32le |
|---|---|---|---|
| `p.bin` / `Data/p.bin` / `Content/Data` | 0 | 0 | 0 |
| `PuzzleScriptHost` / `SubmitCell` / `IsComplete` / `FlagPanelWidget` / `OnTile00Clicked` | 0 | 0 | 0 |
| `puzzle` / `Puzzle` / `tile_` | 0 | 0 | 0 |
| `CTFGame` | 1 @6746425 | 2 @4071648 | 0 |

并 grep 全部容器：`p.bin` 仅出现在 `.pak` 里 **1 次**（就是目录索引里那条文件名本身），
`.ucas` / `.utoc` / `global.*` / `.so` 全 0。
→ **原生 C++ 侧不按名字打开这个文件**（否则 `TEXT("p.bin")` 的 TCHAR 字面量必然留在 `.so`）；
读取它的一定是**被 cook 过的资产属性**（`FFilePath` / 蓝图里填的路径 / DataAsset 字段），
而 `WBP_FlagPanel` 这一批包的载荷恰好就是容器里"有名字没数据"的那批。
**所以离线静态路被结构性堵死**，不是缺工具，是缺那份资产。

**密码学特征扫描（记录备查，均无法归因到游戏代码）**
`AES S-box @0x6F10B8(7279096)`、`ChaCha "expand 32-byte k" @0x49A6040(77202176)`、
`RC4 字样 @7059875/7069116/…`、`MD5 循环常量 @5802384` —— 这些位置附近全是
OpenSSL/引擎的通用代码，没有 `p.bin`/`Puzzle` 之类的开发串相邻，**不能当锚点**。

**载荷密码学穷举（全部否证）**
| 尝试 | 结果 |
|---|---|
| Oodle（**真的调了 §七 的 `libUnreal_patched.so` + `OodleLZ_Decompress`**，载荷起点 0/24/28/32/48） | 5 个起点全返回 NULL → **不是 Oodle** |
| lz4.frame / brotli 解压 | 全抛异常 |
| AES-ECB（17 个候选 key × {16,24,32} B × 4 个起点） | 最高可打印率 0.55（400+ 次试验下即噪声）；且 AES 需 16 对齐，1396 B 不满足 |
| ChaCha20（同 key 集，nonce=0 / 载荷前 8 B / 16 B 零） | 同上，噪声 |

**结论**：`p.bin` 载荷 = 无周期高熵流（H=7.85，重合率 0.013≈随机基线），
算法/密钥都只可能在**缺失的那份资产**或**运行时**里。这条线到此判死，不再投入。

## 十五、GM 亲自做的 ASTC 渲染尝试（13:15–13:32，人类批准安装解码器）

**做了什么**：
1. 用 `tiles_payload.json` 里 16 个候选载荷（各 29,584 B）全部解码 → **全部洋红噪声**（`tiles_cand_montage.png`）。
2. **自己写了一个"平滑度扫描"**定位真载荷：ASTC 6×6 / 256×256 的 mip0 恒为 29,584 B，
   真图相邻像素差应显著小于随机 ⇒ 对两段窗口逐一 16 字节步进解码打分（1.58 ms/次，共 3,813 个候选）：

   - `faithful.bin[12,170,000 .. 12,195,000]`（WBP 区）

**结论（可写死的负面结果）**：**tile 的 ASTC bulk 不在这两段的任何 16 字节对齐位置上**。
⇒ "渲染 10 块 tile" 需要的不是"猜偏移"，而是 **utoc 的真实 chunk 表（offset/length 对）**；

`background` 已裸像素渲染无字；`p.bin` 0 引用=诱饵），**也不在本机能跑起来的游戏里**（黑屏 = 资产加载失败，
