## 程序是什么（已完全解清）

不是 crackme，**没有 flag 校验**。它是一个"ELF 结构检查器"：

```
usage: elfstudy [-q] [-p|-s|-y] [file|-]
```
`main`(0x2a50) 只做三件事：解析选项 → `strncpy` 把 argv[1] 存到 `0xb1c0`、`fopen/fread` 最多 0x10000 字节到 `0xb260`、长度存 `0xb240`
→ `FUN_00104080` 打印 header/phdr/shdr，`FUN_00106dc0` 用全局变量（`b264`=EI_CLASS, `b265`=EI_DATA, `b270`=e_type, `b272`=e_machine, `b278`=e_entry, `b280`=e_phoff, `b288`=e_shoff …）逐字段输出。

判据（真跑过）：
- 全量反编译 174 个函数 / 成功 128；**整个程序里 0 个 XOR 运算**（`grep '\^'` 为空），只有 2 处 `memcmp`（argv 选项比较 + `FUN_00105e00` 字符串相等）。⇒ **不存在解密/校验逻辑**。
- 输出与 `readelf -h/-l/-S` 逐字段一致，无篡改字段。
- `FUN_00105b30` 是 itoa，用 `.rodata@0x8430` 的两位数字表；该表应为 `00..99`(200 B)，实际 207 B：`00..95` + `2` + `93 94 95 96 97 98 99`。属表尾异常，未解出语义（可能是作者生成脚本残留）。

**机制（新结论，且是决定性的）**：整个 208 B 区 = `canonical[0:192] + canonical[185:200] + NUL`。
也就是 **`memmove(table+192, table+185, 15)`**——把 `0x84e9..0x84f7` 的 15 字节向右挪 7 字节写到 `0x84f0`，
末尾 `0x84ff` 仍是原 NUL。⇒ 这是**补丁脚本的错位拷贝残留**，不是"设计好的编码"，
与"作者生成脚本残留"假设一致。**建议把数字表当红鲱鱼**，别再投入。

### 2) 谁用它 / 能否解码 816 B（结论：不能）

- `0x65be..0x6674` 无符号版，同构；`movzbl 0x20(%rsp,%rsi,2)`（`0x66c3/0x66c9`）。

### 4) ★ 隐藏区新结论：空洞是**旧文件的平移拷贝**（+0x60e6）

## §runner5 — oracle 喂输入（96 次）+ 816B 反汇编相位：**两条线索全判死**

### 任务2（先做，2 分钟定性）：816 B blob 不是代码 —— 判死
方法：对偏移 0..15 全相位截断，`objdump -D -b binary -m i386:x86-64`，按 `(bad)`/`.byte`
统计合法指令覆盖字节比例。**关键：必须带随机数据对照**，因为 x86-64 编码极密，随机字节本身
就能解出 ~95% "合法"指令，绝对值毫无意义。

| 输入 | 合法覆盖率 |
|---|---|
| 816 B blob，相位 0..15 | **94.87 % – 95.17 %（完全平坦）** |
| **816 B 随机字节（对照）** | **94.99 %** |
| 真 `.text`（file 0x2540, 816 B，对照） | **99.87 %** |
| 816 B 全 0x00 / 全 0xff | 0 % / 0 % |

相位 0 "胜出" 仅 0.01 pp = 噪声；真代码 99.9 % 且相位会剧烈分离。
⇒ **816 B 正好落在随机基线**，"旧 build .text 片段"假设**判死**。
先前"addend 流第 6/7/5 字节固定为 e9/b6/c0 像 JMP/mov/shift"是幸存者偏差：
这三个值在任意 816 B 里都近乎必然出现。相位 0 反汇编人眼 dump 也全是
荒谬立即数（`movabs eax,ds:0xd95181db19a999d9`）、越界跳转、散落 `(bad)`，无基本块结构。

### 任务1：把程序当 oracle 喂输入 —— 干涸，但挖出 2 个**操作性坑**
24 输入 × 4 模式 = **96 次调用**，全部 exit 0、stderr 空。
逐行对基线自喂做 shape-diff：所有"新行"都只是**标准解析器文案**，且被所改字段完全解释
（改 e_type→`unknown` / `EXEC`，改 machine→`x86` / `RISC-V`，<64 B→`truncated`，
坏 magic→`not an ELF image`）。**没有任何一次出现多余一行、数值异变、提示语或字符串构造**。
528 B 补丁表与 816 B blob 喂进去都只被 magic 检查拒掉，未被当作任何东西解析。

★★ 两个**此前无人记录**的坑（`evidence/Q3uU57zD-jL_MLaH-r5-cli-quirks.md`）：
1. **硬性 64 KiB 输入上限**：喂 65537/100000/200000 B 均只报 `65536 bytes loaded`，
   `/bin/ls`(11352352 B) 也只读 65536。**任何超过 64 KiB 的输入被静默截断。**
2. **文件参数只在 argv[1] 生效**，而 usage 写的是 `elfstudy [-q] [-p|-s|-y] [file|-]`（旗标在前）：
   - `elfstudy -p work/elfstudy.bin` → `[image] 0 bytes loaded` （文件被**忽略**）
   - `elfstudy work/elfstudy.bin -p` → `[image] 43304 bytes loaded` ✓
   ⇒ **按官方 usage 顺序传文件名会静默分析一个空镜像。** 此前任何用 `-p <file>` 形式的
   运行，其结论都是对空输入得出的。模式旗标本身位置无关，只有文件名是位置敏感的。
3. 附带确认：`-q` 是**空操作**（照样打印全部 5 块）；模式是严格划分
   （default=全部/-p=程序头/-s=节头/-y=符号表）。
