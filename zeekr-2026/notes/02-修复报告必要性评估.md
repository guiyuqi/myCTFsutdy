## 1. 管道 bug —— 必须修（已修）

无争议。原实现在产物截断时仍报"完整结果已保存"并 exit 0，
比赛中会让人拿着 3% 的伪代码当完整结果。**这是最危险的一类 bug。**

## 2. 重复运行项目冲突 —— 必须修，且我实测出它更严重

报告的诊断正确：`-import` 不覆盖已导入的同名程序 → 导入失败 → 无收尾行。

**但我实测发现了报告没提到的更坏后果：失败的运行会把上一次的好产物覆盖掉。**

复现过程（真实发生，非构造）：

```
重跑前: decompiled/uhttpd_.c = 6508 行 / 202 个函数体
重跑后: decompiled/uhttpd_.c =   67 行 /   0 个函数体   ← 好产物被覆盖
```

幸好验证者留下的备份 `evidence/verify-decompiled/uhttpd_.c`（202 函数）还在，
已复原。**这比报告描述的"无法重跑"严重得多——它是数据破坏。**

### 修复内容

1. **项目名唯一化**：每次运行用 `fw_<二进制名>_<PID>` 独立项目，跑完 `trap` 自清 → 不再冲突
2. **先写临时文件，校验通过再原子替换** → 失败的运行**不会**覆盖已有产物
3. **脚本目录缺失时显式报错**（原来会静默回退到备用目录，导致"成功"产出空结果）

### 验证结果

| 测试 | 结果 |
|---|---|
| 连续运行两次同一目标 | ✅ 均成功（原必冲突） |
| 失败运行（非 ELF 目标） | ✅ exit=1，**已有产物完好** |
| 脚本目录错误 | ✅ 显式报错 exit=1，不再静默回退 |
| 临时文件 / 脏项目残留 | ✅ 无残留 |
| 完整重跑 | ✅ 6506 行 / 202 函数体 / 收尾行存在 |

## 3. Ghidra 写 `~/.config` —— 条件性必要 ⚠️

报告称在 workspace-write 沙箱下 `~/.config` 只读导致 Ghidra 启动失败，
只能在 `danger-full-access` 下跑通。

**我复核的当前状态：`~/.config` 可写，反编译正常运行（202 函数跑通）。**
说明当时的会话策略与现在不同——可能是报告作者当时的沙箱模式更严。

**但这条依然重要，因为它直接关系到工作区隔离方案：**

- 如果开赛时把工作区收窄到 `~/ctf-2026`（**你原本想做的隔离**），
  且会话处于 `workspace-write`，那么 `~/.config` 就在边界外 → **Ghidra 会失败**
- 后果：比赛时我**无法自主重跑反编译**，每次都要你手动介入

**处理方案（已实施）**：把 Ghidra 配置目录重定向进工作区。

我先试了 `VMARGS_FROM_CALLER="-Duser.home=..."` —— **无效**（JVM 接受参数，
但 Ghidra 仍写 `~/.config`）。真正起作用的是 **`XDG_CONFIG_HOME`**：
Ghidra 的 `ApplicationProperties` 在 Unix 下走 `getDirFromEnv("XDG_CONFIG_HOME")`。

实测确认：

```
$ XDG_CONFIG_HOME=<工作区>/.config analyzeHeadless ...
INFO  Loading user preferences: <工作区>/.config/ghidra/ghidra_12.1.2_PUBLIC/preferences
```

配置（含报告里报错的 `java_home.save`）全部落到工作区内。已在 `fw-env.sh` 中
设置，并尊重调用者已有的 `XDG_CONFIG_HOME` 值、目标不可写时回退 `~/.config`。

**结果**：工作区隔离与反编译可以共存 —— 收窄工作区后我仍能自主重跑反编译。

**注意**：不处理也能用——只要会话保持当前策略（`~/.config` 可写）即可。
所以这是"若要严格隔离才需要"。

## 4. 缺 OpenWrt 库 —— 多半不是问题

报告更正了自己上次的说法，发现真正的阻塞不是 musl loader，而是
`libubox.so.20230523` / `json_script` / `blobmsg_json` / musl libc 这一整组。
**这个更正本身是准确的**（我早先说"只缺 loader"确实不完整）。

**但"需要准备 OpenWrt rootfs"这个结论对比赛场景多半不成立**，理由：

- 固件题给的**要么是完整固件镜像，要么是含 rootfs 的包**
  → 解包后 `/lib`、`/usr/lib` 里天然带着这些库，
  `qemu-<arch>-static -L ./rootfs ./bin/x` 用 `-L` 就能找到
- 只有"单独给一个裸二进制"才会遇到这个问题，
  而那正是我当初放进去的**测试样本**（已标注非题目）的形态
- 而且**纯静态逆向完全不受影响**——202 个函数的伪代码已经够用

**结论：不需要为动态仿真额外准备 rootfs。** 真遇到动态需求时，
`~/ctf/firmware/openwrt-x86-64.img` 这个现成的 OpenWrt 23.05.5 x86_64 镜像
就是合法测试夹具（同一版本号 20230523）。
