- **最终脚本**: `scripts/proto_solve_final.py` + `scripts/oracle.py` / `rb.py` / `pc.py`

## 1. 题目形态

题目只给一句"极简的二进制协议 / 无公开文档 / 需交互还原" + 一个 `nc`。
**没有附件** —— 服务本身就是唯一题面，所有信息必须靠发字节观察响应获得。

## 2. 协议还原结果

```
请求 = uint32 BE length ‖ payload          payload[0] = 操作码
响应 = uint32 BE length ‖ body             body[0] = 状态 (00 ok / 01 err)
payload 上限 4096 字节；>4096 直接无响应
操作码单字节派发，实际只有 1 / 2 / 3（0..255 × 多长度全扫过）
```

| op | 语义 | 响应 |
|---|---|---|
| `01` | 下发会话令牌 | `00` + 48B = `IV(16) ‖ C1(16) ‖ C2(16)`，AES-CBC/PKCS#7 |
| `02` | **填充预言机**：把 `args[-32:]` 按两段 CBC 解密，padding 合法→1 | `00 00` / `00 01` |
| `03` | 取 flag：**同连接**令牌解密出 `role=admin` 才给 | `00`+flag / `01 denied` |
| 其它 | — | `01 "unknown opcode"` |

`op1` 令牌明文（用预言机解出）：`role=user       sid=<8hex>` + `0x04×4`

## 3. 判定链条（关键推理）

1. **`op1` 的输出被 `op2` 100% 接受** → `op2` 校验的是服务器自己产出的东西。
2. **随机 32B 通过率 ≈ 1/256**（实测 15/4000、24/6000、89/21200）→ 这是一个 **8 bit 级别的
   合法性检查**，而不是内容比对、不是 MAC（MAC 应该是 2⁻¹⁶⁰）、不是简单校验和
   （测了 ~600 个 8 bit 函数都不恒定）。
3. **`len(args) % 16 == 0` 才能通过** → 唯一的、最强的结构性线索：**分组密码**。
4. **逐字节突变图**："无关前缀"的长度随令牌而变 —— `op1` 令牌 20B 窗口、
   随机命中样本 17B 窗口。差值正好是 padding 长度：
   `相关字节 = padding_len + 16`（20=4+16，17=1+16）。
   → 这是 **CBC padding oracle 的指纹**（改 C1 中影响 padding 的那几字节才有用）。
5. `op2` 只看最后 32B、IV 不参与校验 → 可以直接当**通用解密预言机**：
   把任意分组放到"最后一块"，前一块自己控制 → 标准攻击恢复 `D(T)`。

## 4. 利用链

```
op1  -> IV ‖ C1 ‖ C2
op2  -> pad_attack() 逐字节恢复 D(C1)、D(C2)        （16 轮 × 256 查询 / 块）
        P1 = D(C1) ^ IV = "role=user       "
        P2 = D(C2) ^ C1 = "sid=<hex>" + 0x04×4
CBC 比特翻转：IV' = D(C1) ^ "role=admin      "     （只改 IV，sid/padding 保持合法）
op3(IV' ‖ C1 ‖ C2)  ->  00 + flag
```

## 5. 两个决定成败的细节（都是最后才撞对的）

1. **令牌与会话绑定**：`op3` 只认"本连接 `op1` 刚下发的那个令牌"派生出的密文。
   在别的连接里提交同一个伪造令牌 → `denied`。
   所以 `op1 → 伪造 → op3` 必须**在同一条 TCP 连接内**完成；
   预言机查询可以另开连接（它无状态）。**这一条耗掉了最多时间。**
2. **role 字段是 16 字节定宽**，必须恰好 `b'role=admin' + b' '*6`。
   `role=admin\0…` / `role=administrat` / `role=admin`+`0x04` / `role=ADMIN` / `admin`
   全部 `denied`。

## 6. 走过的弯路（按代价排序）

| 弯路 | 代价 | 正确做法 |
|---|---|---|
| 误用 `attachments5.zip`（DELTA FORGE）当本题附件，做了一整套离线解 | 大 | 题面说"极简二进制协议 + nc"且**无附件**时，先只打服务 |
| 没尽早试 `len % 16` 对齐 | 大 | 出现"固定 1/256 通过率"时**立刻**扫 `len % 2/4/8/16/32` 的门限 |
| 把 `op2` 当 keyed MAC / 校验和，写了 ~600 个 8 bit 函数猜测器 | 中 | 1/256 + 分组对齐 ⇒ 先怀疑 padding oracle |
| 把"两个不同窗口"当成"析取条件"来解释 | 中 | 那是 **padding_len 不同**导致的窗口长度差，不是两个检查 |
| 用 pipelining 大 batch 探测（一次连接塞几千请求）**静默丢响应**，把"该有解却有 0 解"的异常分析带偏 | 中 | 先给探测框架加**分块 + 重试 + 丢包检测**（`rb.py`），再谈统计 |
| 工具 60s 上限 + `nohup &` 被父进程回收，长任务无输出 | 小 | 用受管后台任务（`run_in_background`），或把长活拆小 |

## 7. 可复用方法论

- **交互题优先级**：先定帧 → 再枚举操作码（含不同长度）→ 再对每个操作码做
  "单字节突变图"（哪些字节影响结果、哪些完全不care）。
  突变图能一次性暴露"窗口结构 / 分组对齐 / padding 依赖"。
- **量化线索 > 语义猜测**：`1/256` 这个数字比任何字符串猜测都有用。
  它直接指向"随机数据以 2⁻⁸ 概率满足的合法性检查"（padding / 1 字节 tag / 边界）。
- **长度门限要单独扫**：`len % N == 0`、`len >= N`、`len == N` 是三类不同设计。
- **服务器自己产出的东西一定合法** ⇒ 用它当"已知良好样本"，与随机样本对比差异，
  能最快定位校验目标（这里就是 20B vs 17B 窗口差 3 字节 = padding 长度差）。
- **无状态预言机 + 有状态会话要分开对待**：先测"跨连接是否等价"，
  再决定利用脚本要不要把连接一直握着。
