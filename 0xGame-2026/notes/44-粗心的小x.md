# 44 · 粗心的小x（AI / 凭据泄露，854 分）

- **flag**: `0xGame{D0_n0t_uplO@d_pr1v4t3_th1ngs_t0_g1t}`
- **提交**: `{"code":200,"msg":"OK","data":{"result":true}}` ✅
- **出处**: `AI-chat-project.zip` 内嵌 `.git/` 的对象库 + `chat_export.json`
- **复现脚本**: `scripts/44-solve.py`
- **证据**: `evidence/44-solve-output.txt`、`evidence/44-git-log.txt`、`evidence/44-submit.log`

## 一句话

小 x 把 `.env` 提交进了 git，又把 API KEY 贴到 ChatGPT 里；三个 "API KEY" 其实
都是 `sk-` + base64(`partN:<flag 片段>`)，三段一拼就是 flag。

## 关键点

1. zip 里**带完整 `.git/` 目录**（`.gitignore` 只写了 `__pycache__/ *.pyc .venv/`，
   **没有忽略 `.env`** —— 这是最典型的凭据泄露）。
2. flag 被拆成 3 段，分别藏在 3 个不同的地方，缺一不可：

   | 片段 | key | 藏在哪 |
   |---|---|---|
   | `part1: 0xGame{D0_n0t_` | `sk-T7xQcGFydDE6MHhHYW1le0QwX24wdF8` | `chat_export.json`（小 x 手贴给 ChatGPT 的那个） |
   | `part2: uplO@d_pr1v4t3` | `sk-m2PzcGFydDI6dXBsT0BkX3ByMXY0dDM` | **git 历史** commit `79edd41` 里 `chat.py` 硬编码的 key（后续 refactor 删掉了 → 必须 `git log -p` 才能看到） |
   | `part3: _th1ngs_t0_g1t}` | `sk-W9kDcGFydDM6X3RoMW5nc190MF9nMXR9` | `.env`（工作树与 HEAD 都在；`.env` 从 initial commit 起没改过） |

3. **解码细节（坑）**：`sk-` 后面紧跟的 **4 个字符是出题人加的盐**，
   整串 base64 解出来的明文前 3 字节是垃圾（如 `b'O\xbcP'`），
   从第 4 字节起才是 `partN:...`。所以必须按"解出来含 `part`"来定位，不能按偏移猜。
4. 另有第 4 个 key `sk-F4k3VGhpc19pc19hX2Zha2Vfa2V5` → base64 得
   `This_is_a_fake_key`（`.env` 里标注 "旧的测试 key，已吊销"），是**诱饵**。
5. 第 3 段的 key 用了 URL-safe 风格，把 `+` 替换成 `@`（`uplO@d`）；
   还原 `@`→`+` 才能正确解码（脚本里两种都试）。
6. `chat_export.json` **不是合法 JSON**（第 11 行缺逗号，行 15 的 key 后面直接跟着
   中文字符），`json.load` 会报错 —— 别被绊住，直接 `strings`/正则提取 `sk-...` 即可。

## 已排除的方向

- **不存在的 LLM 端点**：`.env` 里 `OPENAI_BASE_URL=https://api.openai.com/v1`，
  key 全是伪造的（`This_is_a_fake_key` 已经明示），**没有任何本地/远程靶机端点**，
  题目 brief 也写明 `需要容器: False`。**没有对 api.openai.com 发任何请求**（也无需发）。
- **dangling blob / stash / reflog 单独分支**：`git fsck` 无输出，`git stash list` 为空，
  所有对象都能从 5 个 commit 到达 —— 本题的"历史泄露"就是普通 commit 的 diff。
- **把 key 当解密密钥**：无加密文件，key 本身即载荷。
