## 解题链（5 步）

### 1. 收集凭据（分布在三个"不该贴"的地方）

| 凭据 | 出处 |
|---|---|
| 账号 `nightowl` | 告示牌 A「值班公共账号」 |
| 口令 `watch2026` | **打印机卡纸第 2 页**「口令已更新为 watch2026」 |
| 终端能力 | 值班手册第 1 页：聊天框直接敲 `/ops help` |

手册第 3 页明写「口令自己找，**总有人贴在不该贴的地方**」——口令确实被违规贴在打印机里，这是题目的第一层叙事。

### 2. `/ops help` 拿到全部子命令

```
login <账号> <口令>        登录终端
whoami                   当前会话
logs [--since HH:MM]     查看事件日志
backup list              列出我的备份
backup restore --id N    恢复指定备份
door unlock <门禁码>      开启安全屋门禁
logout                   注销
```

### 3. 建立时间线（`logs --since 02:50`）

手册第 3 页「备份服务每晚 **02:50** 例行执行」+ 告示牌 B「workstation-07 最后在线 **03:17**」
这两条就是让我们去查 02:50 之后的日志：

```
02:50:03  backupd  scheduled backup #7 stored (owner: chensy, tag: handover-final)
02:58:44  chensy   login ok (workstation-07)
03:11:08  chensy   backup restore --id 7 -> OK
03:17:55  chensy   session lost (workstation-07 offline, no logout)
03:19:02  door     safe-room unlocked with emergency code
03:19:41  door     safe-room auto-locked
```

**日志直接泄露了两件事**：备份 `#7` 的归属是 `chensy`（不是我们），以及它的 tag 是 `handover-final`。

### 4. ★ 越权恢复他人备份（本题核心漏洞）

`backup list` 的响应末尾特意写着「（**仅显示当前账号名下的备份**）」，而 `nightowl` 名下只有 `#2` / `#5`。
卡纸第 1 页的运维公告则明说：

> `backup restore` 模块的**归属校验仍在开发中，预计下周上线**，期间请各位按规范操作。

→ 这是**被题目主动点名的 IDOR**：`restore` 时服务端不校验 `owner`，于是可以恢复 `chensy` 的 `#7`。

```
/ops backup restore --id 7
restore #7 -> OK (owner: chensy, tag: handover-final)
    交接文档
    我搬去安全屋住了，别找我。
    真有天大的事再来：门禁码 3117。
    服务器交给你们了。—— 老陈
note: handover-final 已归档。
```

手册第 3 页「**门禁码只存在交接文档里，纸上一律不写**」在此闭环——门禁码只能靠越权拿到备份才能得到。

### 5. 开门禁拿 flag

```
/ops door unlock 3117
```
进入安全屋，告示牌上写着 flag。

## 设计点评（值得记的几点）

1. **叙事与漏洞是同一件事**：三页手册把账号位置、口令违规张贴、备份时间、门禁码存放位置全部说清楚，
   而两个故意埋的缺陷（`restore` 无归属校验、口令贴错地方）都被剧情合理化了——不是硬塞提示。
2. **日志是最强的路标**：`logs --since 02:50` 一次性给出"别人的备份编号 + tag 含义 + 应急码存在"，
   把盲试 `--id` 的暴力路径变成一条直路。这也是为什么这题不该去暴力枚举备份编号。
3. **门会自锁**：日志里 `03:19:41 safe-room auto-locked` 提示解锁后要尽快进入。
