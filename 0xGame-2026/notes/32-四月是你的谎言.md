## 1. 协议（原文逐字节）

连上即打印固定 banner，参数**跨连接完全一致**（连 3 次比对，`32-banner{,2,3}.txt`）：

```
message = YOU DID LIVE IN MY HEART
hash(key+message) = 46af62962126aa38e4f1680a6c64bc6b
please echo the mission in hash(key+message+response)

new longing: <输入一行>
```

读完一行输入后：若比较通过则给 flag，否则回：

```
not matter,moon and sun have their next April
```

**任何 ASCII 输入都得到同一句**（长度 0/1/5/16/31/32/63/64/100 全测过）。
输入含**非 ASCII 字节**时服务自己抛异常（见下）——这暴露了 `challenge.py` 的内部结构。

## 2. ★ 服务源码结构泄露（异常回溯）

发 `\x80\n` 会拿到未捕获异常的完整回溯：

```
Traceback (most recent call last):
  File "/app/challenge.py", line 47, in <module>
    main()
  File "/app/challenge.py", line 40, in main
    if compare_digest(submitted_hash, expected_hash):
       ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
TypeError: comparing strings with non-ASCII characters is not supported
```

**可读出的事实**：
- 比较语句为 `compare_digest(submitted_hash, expected_hash)`，**行号 40**，`main()` 在 47 行被调用。**全文只有 47 行**。
- 该行是 `if` 而不是 `assert`，说明**正常路径下比较是能返回的**（即两个操作数通常都是纯 ASCII 字符串）。
- 一旦我提交的值带非 ASCII，`compare_digest` 对 **str** 做比较就崩 → 证明 `submitted_hash` 是**由我的输入直接构造的字符串**（不是 hex 摘要：hex 恒为 ASCII，永远不会触发这个 TypeError）。

## 3. ★★ 密钥恢复（本题的密码学核心，已 100% 确认）

`hash(key+message)` 是 32 位 hex ⇒ MD5（若为 SHA-256 应为 64 位）。

对 key 做穷举：

```python
import hashlib
MSG = b"YOU DID LIVE IN MY HEART"
T   = "46af62962126aa38e4f1680a6c64bc6b"

# 全 1 字节(256) + 全 3 字节(2^24) 穷举：无命中
# 全 2 字节(65536) 穷举：唯一命中
KEY = bytes.fromhex("2026")      # == b" &"  (0x20, 0x26)
assert hashlib.md5(KEY + MSG).hexdigest() == T   # ✅
```

- **1 字节**：无解。
- **2 字节**：**唯一解** `b" &"`（全 65536 空间穷举，只有它命中）。
- **3 字节**：全 `2^24` 空间穷举，**无解**。

### 密钥的语义（关键洞察）

```
bytes.fromhex("2026") = b" &"   →   0x20 = ' ' ，0x26 = '&'
```

即 **密钥就是把十六进制串 `2026` 当作“字节对”来解释**：`0x20 0x26`。
而 `2026` 正是**同作者第 7 题**题面里给的 passphrase「密码是 **0x2026**」。
⇒ 作者把 `0x2026` 从“字符串口令”改成了“两个字节 `20 26`”。这与 9 号/11 号
「哈希/编码口径是主要陷阱」的同作者规律完全吻合。

## 4. 卡点：最终 flag 口径无法确定

服务自称要求 `hash(key+message+response)`，但**它从不给出 `expected_hash`**。
已知 key 后我能对任意 response 算出摘要：

| response | md5(key+msg+response) |
|---|---|
| （空） | `46af62962126aa38e4f1680a6c64bc6b`（= banner 本身） |
| `TOO` | `dce3a976b3d56922335d58726ead0f38` |
| ` TOO` | `38974fe284844e99ebe23cd923ff596e` |
| `TOO\n` | `12f0e50fc836d55fa34d64ab8b3090b4` |
| `I LOVE YOU TOO` | `622d69f24cab588cb3852174c5fb40c1` |
| `YOU DID LIVE IN MY HEART TOO` | `1e8801b2260554ad884b4090ca417878` |

**live 测试全部返回同一句 `not matter,...`**（含把上述摘要本身作为 response 回填、
含原始 16 字节二进制摘要）——即服务侧的比较**从来没有通过**，且服务对 response
的具体取值**没有任何可观测反馈**（无差异、无时序差、无二次输入）。

### 已排除的方向

1. **MD5 length extension**：已完整实现并自测通过（`work/32_lie/md5le.py`，0 失败）。
   用 klen=0..64 全枚举生成伪造 response 提交，**回复不变**。原因是本题构造是
   `md5(key‖message‖response)`（response 在**后**），length extension 得到的是
   另一个摘要，而服务不给目标摘要，无法闭环。
2. **key 就是字面 `0x2026`**：`md5(b"0x2026"+MSG)` ≠ banner；只有字节对 `20 26` 才命中。
3. **flag 直接是密钥文本**：提交 `0xGame{ &}` → `{"code":402,"msg":"flag错误"}`。
4. **`TOO` 直接把 banner 摘要撞出来**：需要真正的 MD5 碰撞，不可行。
5. **绕过比较**：`compare_digest` 只在**同类型**下工作，str 对 bytes 会直接
   `TypeError`（已实测）——不存在“类型混淆使其恒真”的捷径。

## 5. 给下一个接手者的最短路径

- 密钥已锁定：`bytes.fromhex("2026")`，`md5(key+b"YOU DID LIVE IN MY HEART")`
  必须等于 banner 摘要（可本地断言）。
- **唯一缺的是“服务期望的摘要值/清洗规则”**。第 8 题就是死在这一点上——
  不要重演：**在没有可复现依据前不要再提交**。

  「response 后面加 TOO」到底加在**哪一侧**、以及是否要带引号/空格。
  `0xGame{ &}` 与 `0xGame{TOO}` 已各试一次，均 402。
